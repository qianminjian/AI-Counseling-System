# 13 领域词汇表（Domain Glossary）

> 用途：架构审查、设计讨论、代码探索的统一术语表。所有设计文档与代码讨论应使用本表术语，避免漂移为「组件/服务/API/边界」等泛化词。
> 维护：新领域术语出现时（命名深化模块/新增业务概念）即时补充；与 design/01-12 主文档保持同源。

## 11. 架构词汇表（深化审查用语）

| 术语 | 定义 |
|------|------|
| 模块（Module） | 代码库中承载一个概念的单元（类/包/文件集合），边界由概念而非技术分层决定 |
| 接口（Interface） | 模块对外的暴露面（方法签名、参数、返回），宽度与复杂度之和 |
| 深度（Depth） | 模块接口简洁、内部实现复杂度高（隐藏细节多）——「浅模块」= 接口复杂度≈实现复杂度 |
| 接缝（Seam） | 一个可以替换实现、隔离依赖的点；「一个适配器=假设性接缝，两个=真实接缝」 |
| 适配器（Adapter） | 在接缝处隔离外部依赖（DB/LLM/HTTP）的模块，接口由领域定义而非依赖定义 |
| 杠杆（Leverage） | 一处修改传导到多处行为改善（注册表/单一规则源的收益） |
| 局域性（Locality） | 理解一个概念所需跳转的模块数量——概念相关代码应就近放置，规则不散落 |
| 删除测试（Deletion Test） | 问「删除这个模块：复杂度被集中（好）还是被移动（坏）？」——集中=深化机会，移动=转发层 |
| 假功能（Fake Feature） | 「测试绿、生产死」：消费端已实现且有单测，生产端信号恒 null/未接线 |
| 僵尸参数（Zombie Parameter） | 接口参数在生产唯一调用点恒传固定值，实现内分支永不进入 |
| 上帝类 / 神组件（God Class / God Component） | 单类/单组件承载多种职责、构造器依赖或 hooks 数量失控（如 826 行/22 依赖） |
| 失败安全（Fail-safe） | 依赖（存储/网络/认证）不可用时回退默认值或降级路径，不抛未捕获异常导致白屏/中断（如 localStorage SecurityError → 默认值） |
| 可观测性（Observability） | 失败路径打点计数 + 结构化日志 + 告警阈值；静默 catch 清零——「失败不可观测 = 无告警」 |
| 台账一致性（Ledger Consistency） | 文档/台账登记状态与代码事实一致；审计发现失实（行数/状态/断言）即日修正并留痕 |

## 12. 术语使用约定

1. 代码讨论与设计文档优先使用本表术语（如「会话」而非「conversation 服务」、「接缝」而非「边界/API」）
2. 新增领域概念并命名深化模块时，先在本表登记再落地代码
3. 术语含义与 design/01-12 主文档冲突时，以主文档为准并同步本表
4. 本表常驻 design/ 目录，不随 doing 子文档合并/归档
