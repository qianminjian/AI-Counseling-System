# 42 - 部署架构升级设计（蓝绿部署 + CDN + 前端代码分割）

> 创建：2026-07-28 | 状态：设计完成，待实施 | 对应规划任务：OPS-006 + PERF-003（design/30 §方向四、方向八）
>
> 定位：把当前"单实例 + 手动部署 + 无 CDN + 前端整包加载"升级为**零停机发布 + 静态资源 CDN 加速 + 前端路由级代码分割**，目标是发布不中断服务、首屏加载更快、承载用户量增长。触发时机为**用户量增长 / 对发布可用性有要求**（P2）。本文与 design/40（水平扩展）共享 nginx upstream 机制，是其部署侧落地。

---

## 一、业界对标（避免空想的依据）

### 1.1 零停机发布的三种范式

| 范式 | 机制 | 资源成本 | 回滚速度 | 适用 |
|------|------|---------|---------|------|
| **蓝绿部署（Blue-Green）** | 同时存在两套完整环境（蓝=旧、绿=新），流量一次性从蓝切绿；出问题切回蓝 | 高（双份资源） | 秒级（切回） | 需即时回滚、发布风险敏感 |
| **滚动发布（Rolling）** | 逐个替换实例（停一个旧、起一个新），新旧共存过渡 | 低（无需双份） | 中（逐个回滚） | 无状态多副本、资源受限 |
| **金丝雀（Canary）** | 先放小比例流量到新版本，观察无误再全量 | 中 | 快 | 需灰度验证、A/B |

**选型结论**：
- 本系统后端在 design/40 无状态化后天然支持**滚动发布**（多副本逐个替换）；对**风险敏感的大版本**辅以**蓝绿**（双环境 + nginx upstream 一次性切换）。
- Docker Compose 层面：滚动发布用 `deploy.update_config`（`order: start-first`，先起新后停旧）；蓝绿用双 compose 环境 + nginx upstream 切换。
- 金丝雀依赖流量按比例切分，属后续演进（需服务网格或 nginx 加权 upstream），本期不做（YAGNI）。

### 1.2 优雅关闭与健康检查（零停机的前提）

零停机的关键不在"起新"，而在"**停旧不断连接**"：

1. **健康检查**：新实例 `/actuator/health` 就绪前，LB 不得导流（避免把请求打到没准备好的实例）。
2. **优雅关闭（graceful shutdown）**：旧实例收到停止信号后，先从 LB 摘除、停止接收新请求、等待存量请求（含 SSE 流）处理完再退出。Spring Boot `server.shutdown=graceful` + `spring.lifecycle.timeout-per-shutdown-phase` 提供该能力。
3. **连接排空（connection draining）**：nginx/LB 层面给旧实例设置 draining 窗口。

> 本系统已配 Spring Boot 优雅关闭与容器健康检查（见 §2.1），是升级的良好基础。

### 1.3 CDN 与前端性能（Web Vitals 导向）

- **静态资源 CDN**：JS/CSS/图片/字体等静态产物由 CDN 边缘节点就近分发，降低首字节时间（TTFB）、卸载源站带宽。教育场景用户地理分散，CDN 收益明显。
- **前端代码分割（code splitting）**：按路由/组件懒加载，只在需要时下载对应 chunk，减小首屏 JS 体积——对标 Web Vitals 的 LCP/FID 优化。Vite（本系统构建工具）通过 `build.rollupOptions.output.manualChunks` 与动态 `import()` 实现。
- **缓存策略**：带 hash 的静态资源用长期强缓存（`Cache-Control: immutable`），HTML 入口用协商缓存，保证发版即时生效又最大化缓存命中。

## 二、现状与差距（基于代码基线审计）

### 2.1 部署现状

| 维度 | 现状 | 差距 |
|------|------|------|
| 后端实例 | 单实例（`docker-compose.prod.yml`，`container_name: mindsafe-backend`，无 replicas） | 零停机需 ≥2 实例可逐个替换 |
| 发布方式 | 手动 `deploy.sh`（rebuild + restart），**发布期间服务中断** | 需 start-first 滚动 / 蓝绿切换 |
| nginx 上游 | `proxy_pass http://backend:8080`（无 upstream 块，单点） | 需 upstream 池支持多实例切换 |
| 健康检查 | ✅ 容器 healthcheck 已配 | 复用于 LB 导流判定 |
| 优雅关闭 | ✅ Spring Boot 优雅关闭具备基础 | 需与 LB 摘除/draining 协同 |
| 依赖服务 | Redis 7、postgres（pgvector/pgvector:pg16）已在 compose | — |

### 2.2 CDN 与前端加载现状

| 维度 | 现状 | 差距 |
|------|------|------|
| CDN | 无，静态资源由源站 nginx 直出 | 需接入 CDN（源站回源 + 边缘缓存） |
| 学生端代码分割 | **无 `manualChunks` 配置**；`transformers.web-*.js` 约 516KB 已作按需动态 chunk（且排除 PWA 预缓存） | 需路由级懒加载 + 第三方大库单独分包 |
| base 路径 | 学生端 `base='/mindsafe/'` | CDN 路径需与之协调 |
| PWA 缓存 | VitePWA 已配，API 走 NetworkOnly runtimeCaching | 静态资源缓存策略与 CDN 协同 |
| 前端产物 | 三前端（student-h5 / teacher-web / parent-h5）Vite 构建，Dockerfile 打包 | 分割策略需分别评估 |

## 三、后端零停机发布设计

### 3.1 滚动发布（默认，无状态化后适用）

前提：design/40 完成无状态化（会话/缓存/广播全部外置），后端可多副本对等运行。

```
初始： nginx upstream = [backend-1(v1), backend-2(v1)]
步骤1： 起 backend-1(v2)，健康检查通过 → 加入 upstream
步骤2： backend-1(v1) 从 upstream 摘除 → 优雅关闭（排空存量请求）
步骤3： 对 backend-2 重复 步骤1-2
结果： upstream = [backend-1(v2), backend-2(v2)]，全程有实例在线
```

| 项 | 设计 |
|----|------|
| Compose 编排 | `deploy.update_config.order: start-first`（先起新实例，再停旧实例） |
| 健康门禁 | 新实例 `/actuator/health` = UP 前不接流量 |
| 优雅关闭 | 旧实例先摘 upstream → `server.shutdown=graceful` 等待存量请求（含 SSE）完成 → 退出；设超时上限 |
| SSE/WS 处理 | 长连接在旧实例排空窗口内自然结束或客户端重连到新实例（design/40 AC-4 保证重连不丢状态） |

### 3.2 蓝绿部署（风险敏感的大版本）

```
蓝环境（当前生产 v1）  ← nginx upstream 指向蓝
绿环境（部署 v2，独立一套）
   ↓ 绿环境全量健康检查 + 冒烟测试通过
nginx upstream 一次性切到绿  ← 流量瞬时切换
   ↓ 观察期（绿稳定）
下线蓝（或保留作即时回滚）；出问题：upstream 切回蓝（秒级回滚）
```

| 项 | 设计 |
|----|------|
| 环境隔离 | 蓝绿各一套 backend 副本组；共享 Redis/Postgres（数据层不双份，见 §3.3 约束） |
| 切换机制 | nginx upstream 变更 + reload（或用 nginx 变量 + 双 upstream 块切换 `proxy_pass`） |
| 冒烟门禁 | 切换前对绿环境跑关键路径冒烟（复用 `tests/e2e/smoke-test.sh`） |
| 回滚 | 保留蓝环境一个观察周期，upstream 切回即回滚 |

### 3.3 数据层兼容约束（蓝绿的关键风险）

蓝绿/滚动发布时新旧版本**共享同一个数据库**，因此：

- **数据库迁移必须向后兼容**（expand-contract 模式）：先加列/表（旧版本忽略），双版本共存期都能跑，待旧版本全下线后再删旧结构。**禁止发布即删列/改类型的破坏性迁移**——否则旧实例在过渡期崩溃。
- schema 变更属红线（AGENTS §5 红线 3），迁移脚本须评审向后兼容性。
- 会话状态/缓存已在 Redis（design/40），新旧版本读写同一 Redis，需保证状态结构向后兼容或加版本字段。

## 四、CDN 与前端代码分割设计

### 4.1 CDN 接入设计

| 项 | 设计 |
|----|------|
| 加速对象 | 三前端静态产物（JS/CSS/图片/字体/wasm 模型文件） |
| 回源 | CDN 边缘未命中回源站 nginx；HTML 入口不做长缓存（保证发版生效） |
| 缓存分层 | 带 content hash 的资源 `Cache-Control: max-age=31536000, immutable`；`index.html` 协商缓存（ETag/no-cache） |
| base 协调 | 学生端 `base='/mindsafe/'` 需与 CDN 域名/路径前缀一致；产物引用路径正确指向 CDN |
| wasm 大文件 | `transformers.web-*.js`（~516KB）等模型文件走 CDN，减轻源站；PWA 已排除其预缓存，与 CDN 按需下载协同 |
| 合规 | 教育数据合规要求下，CDN 仅缓存静态公共资源，**绝不缓存含 PII 的 API 响应**（现有 API 已 NetworkOnly） |

### 4.2 前端代码分割设计（Vite manualChunks + 路由懒加载）

以学生端为主（当前无 manualChunks，首屏包含全部代码 + 大依赖）：

| 分割维度 | 设计 |
|---------|------|
| 路由级懒加载 | 非首屏路由用动态 `import()`，按页面切 chunk（对话页/工具箱/画像/设置分别独立） |
| 第三方大库分包 | 把 `transformers`、图表库、音视频处理等大依赖 `manualChunks` 单独成 vendor chunk，与业务代码解耦，利于缓存复用（业务改动不使 vendor 缓存失效） |
| 首屏最小化 | 首屏只加载"进入对话"所需最小 JS；语音唤醒/SER 等重能力按需异步加载 |
| 预加载提示 | 对高概率下一跳路由用 `<link rel="prefetch">` 预取，平衡首屏体积与后续流畅 |
| PWA 协同 | manualChunks 后产物文件名变化，需同步 VitePWA 预缓存清单（避免大 chunk 被全量预缓存拖慢首装） |

> 三前端分别评估：学生端（重，优先级最高）、teacher-web（中）、parent-h5（后续可能小程序化，见 design/43，代码分割收益视迁移决策）。

### 4.3 缓存与发版一致性

- 静态资源 hash 命名 + 强缓存 → CDN 命中率高、发版不串版本。
- `index.html` 不强缓存 → 发版后用户拉到新 HTML，HTML 内引用新 hash 资源，实现原子切换。
- Service Worker（PWA）更新策略需与 CDN 配合：新版本 SW 激活时清理旧缓存，避免加载到混合版本资源。

## 五、实施路径

| 阶段 | 内容 | 依赖 | 说明 |
|------|------|------|------|
| D-1 | nginx 单点 → upstream 池 | design/40 §3.5 | 与水平扩展共用，先落地 |
| D-2 | 后端多副本 + start-first 滚动发布 | design/40 无状态化完成、D-1 | 默认零停机方式 |
| D-3 | 优雅关闭 + LB 摘除/draining 协同 | D-2 | 停旧不断连接 |
| D-4 | 蓝绿双环境 + upstream 切换 + 冒烟门禁 | D-2/D-3 | 大版本发布用 |
| D-5 | 前端代码分割（学生端优先） | 独立可并行 | manualChunks + 路由懒加载 |
| D-6 | CDN 接入 + 缓存策略 | D-5（产物 hash 化） | 静态资源边缘加速 |

> D-5/D-6（前端性能）与 D-1~D-4（后端发布）相互独立，可并行推进。D-2 强依赖 design/40 无状态化——**未完成无状态化前不得开多副本滚动**（否则会话丢失）。

## 六、EARS 验收标准

| # | EARS 描述 |
|---|-----------|
| AC-1 | When 执行滚动发布，the 系统 shall 全程保持至少一个健康实例在线，用户请求成功率不因发布下降（零停机） |
| AC-2 | While 旧实例被替换，when 其上存在进行中的 SSE 对话流，the 系统 shall 在优雅关闭窗口内让其完成或客户端无缝重连到新实例 |
| AC-3 | When 蓝绿切换后发现新版本异常，the 运维 shall 通过 upstream 切回旧环境在秒级完成回滚 |
| AC-4 | The 所有数据库迁移 shall 向后兼容（expand-contract），保证发布过渡期新旧版本共库不崩溃 |
| AC-5 | When 用户首次加载学生端，the 首屏 JS 体积 shall 显著小于当前整包（大依赖与非首屏路由不在首屏加载） |
| AC-6 | While 静态资源经 CDN 分发，the 带 hash 资源 shall 命中长期强缓存，且发版后用户 shall 通过新 index.html 原子加载到新版本资源，无版本错配 |
| AC-7 | The CDN shall 仅缓存公共静态资源，绝不缓存含 PII 的 API 响应 |
