# 38 - 计费配额与运营后台设计

> 创建：2026-07-28 | 状态：设计完成，待实施 | 对应规划任务：BIZ-004 计费与配额（P2）+ BIZ-006 运营后台（P2，AdminPanel 扩展）（design/30）
>
> 定位：把 design/09 的商业模式（三档年费）落成可执行的**订阅-权益-计量-配额**技术体系，并为平台方提供运营后台。**本期不做在线支付**——学校采购走对公转账+合同（design/09 明确的 To B/To G 采购逻辑），系统内只做订阅登记、权益开关、用量计量与配额管控。

---

## 一、业界对标（避免空想的依据）

### 1.1 SaaS 计费系统的标准分层（Lago / Stripe Billing / Metronome 共性架构）

```
计量 Metering（原始用量事件，只增不改）
  → 聚合 Aggregation（按租户/周期/指标汇总）
    → 权益 Entitlement（订阅计划 → 功能开关 + 配额上限）
      → 评级 Rating（用量 × 单价 → 金额）→ 账单 Invoicing
```

借鉴决策：
1. **计量与计费分离**：用量事件独立落库（不可变、可审计），计费规则改变不影响历史数据——本期只建"计量 + 权益 + 配额"三层，Rating/Invoicing 留到有在线支付需求时再建（YAGNI）
2. **Entitlement 单独建模**（Lago/Stigg 的核心经验）：功能开关矩阵不硬编码在业务代码里，业务代码只问"这个租户有没有 X 权益 / 还剩多少额度"
3. **用量透出给客户**（Stripe/AWS 实践）：学校管理员必须能自己看到用量与余量，否则每次续费谈判都变成扯皮
4. **宽限期（grace period）** 是 B2B 订阅的标配：到期/超额不立即断服务，先降级+通知

### 1.2 配额执行的工程共识

- 配额校验在**网关/过滤器层**统一执行（design/07 已定此原则），返回 **429 + X-RateLimit-Limit / Remaining / Reset** 头（IETF 草案标准，GitHub/Stripe API 同款）
- 计数用 Redis 原子操作（INCR + TTL），**异步落库对账**——同步写库会把配额检查变成性能瓶颈
- **软限制优先于硬限制**：达到 80%/95% 先告警，只有明确列入"硬限"的指标才拒绝服务

### 1.3 教育行业特殊约束（区别于通用 SaaS）

- **心理危机服务永不因欠费/超额中断**：S0-S1 预警链路、SOS、热线展示不受任何配额与订阅状态影响（伦理红线，写入 §四.3 豁免清单）
- 学年制周期：订阅周期按学年（9.1-8.31）而非自然年，与学校预算周期对齐（design/09 采购逻辑）

## 三、订阅与权益模型

### 3.1 数据模型（public schema，平台级数据，非租户 schema）

```
plans 计划表（平台维护）
  id, code(basic/pro/flagship), name, price_per_student_year, status

plan_entitlements 权益矩阵（计划 → 权益项）
  plan_id, feature_key, feature_type(bool/quota), quota_value, quota_period(year/month/day)

subscriptions 订阅表（租户 → 计划）
  id, tenant_id, plan_id, student_seats(购买人数), start_date, end_date,
  status(trial/active/grace/expired/suspended), grace_days(默认30),
  contract_no(合同号), notes    -- 无支付字段，对公转账线下完成

subscription_overrides 单校定制（谈判特例）
  subscription_id, feature_key, quota_value    -- 覆盖计划默认值
```

### 3.2 权益项清单（feature_key，依据 design/09 功能分层矩阵数据化）

| feature_key | 类型 | 基础版 | 专业版 | 旗舰版 |
|-------------|------|--------|--------|--------|
| `ai_chat` | bool | ✗（仅量表+工具箱） | ✓ | ✓ |
| `ai_chat_sessions` | quota/月/生均 | — | 30 | 60 |
| `tts_minutes` | quota/月/校 | 0 | 2000 | 6000 |
| `crisis_alert` | bool | ✓（基础短信） | ✓ | ✓ |
| `assessment_scales` | quota（可用量表数） | 2 | 全部免费量表 | 全部（含授权量表） |
| `parent_h5` | bool | ✗ | ✓ | ✓ |
| `region_dashboard` | bool | ✗ | ✗ | ✓ |
| `api_access` | bool | ✗ | ✗ | ✓ |
| `sms_count` | quota/学年/校 | 500 | 3000 | 10000 |

> 具体数值为设计基线，上线前由商务按 design/09 校准；数值全部在数据库，改价不改代码（开闭原则）。

### 3.3 订阅生命周期

```
trial(90天试用, design/21 试用准入) → active → [到期] grace(30天宽限,横幅提醒+功能保留)
                                            → expired(降级为只读: 教师可看历史,学生端仅工具箱+SOS)
                                            → [续约] active
suspended(平台手动暂停,如合同纠纷) —— 任何状态可进出
```

到期前 90/30/7 天自动通知平台运营 + 学校管理员（notification 包既有通道）。

## 四、计量与配额执行

### 4.1 计量事件流

```
业务动作 → UsageMeter.record(tenantId, metric, qty, refId)
  → ① Redis HINCRBY usage:{tenantId}:{metric}:{period}   （实时计数，配额检查用）
  → ② usage_events 表异步批量落库（不可变事件，对账与审计用）

usage_events: id, tenant_id, metric, quantity, ref_type, ref_id, occurred_at
usage_daily 聚合表: tenant_id, metric, day, total   （夜间任务对账 Redis vs events）
```

计量指标（与权益 quota 一一对应）：`ai_chat_session`、`tts_minute`、`sms_send`、`assessment_submit`、`api_call`。

### 4.2 配额执行点（Filter 层，counseling-api）

```
请求 → JWT 解析 tenantId → EntitlementFilter：
  1. bool 权益：无权益 → 403 {code:30002, "当前版本不包含此功能"}
  2. quota 权益：Redis 计数 ≥ 上限 → 429 {code:30001} + X-RateLimit-* 头
     80%/95% 阈值 → 异步事件通知学校管理员与平台（不阻塞请求）
```

### 4.3 豁免清单（硬编码保护，任何配置不可覆盖）

以下链路**永不做配额/订阅拦截**：

1. S0-S1 预警生成、通知、电话升级全链路
2. SOS 页面与热线资源接口
3. 危机场景短信（`sms_send` 计量照记，但不拒发；超额部分账期内结算）
4. 教师端预警处理工作流（design/35）

> 落地方式：豁免接口打 `@QuotaExempt` 注解（白名单显式声明），EntitlementFilter 直接放行；豁免清单变更需走 design/32 发布评审。

### 4.4 降级体验（超额/过期时的用户感知）

| 场景 | 学生端 | 教师端 |
|------|--------|--------|
| AI 会话配额用尽（当月） | 波波："这个月和波波聊的时间用完啦，先去百宝箱玩玩吧"→ 工具箱仍可用 | 横幅提示 + 用量页入口 |
| TTS 分钟用尽 | 静默降级纯文字（不报错） | 用量页可见 |
| 订阅 grace | 无感知 | 顶部续费提醒横幅 |
| 订阅 expired | 仅工具箱 + SOS | 只读模式横幅 |

## 五、学校管理员用量视图（teacher-web 内，管理员角色）

新增"订阅与用量"页面（仅学校管理员角色可见）：

- 订阅卡片：当前版本、席位数、有效期、距到期天数
- 用量仪表：各 quota 指标本周期用量/上限进度条（数据源 `usage_daily` + Redis 实时数）
- 月度用量趋势图（近 6 个月）
- **不展示金额**——价格谈判是线下商务行为，系统内只见版本与用量

API：`GET /api/v1/tenant-admin/subscription`、`GET /api/v1/tenant-admin/usage?period=`。

## 六、平台运营后台（BIZ-006，扩展 /api/v1/platform/*）

服务对象：平台运营人员（非学校）。独立前端入口（AdminPanel 扩展），平台级 RBAC（超管/运营/客服三角色）。

### 6.1 功能模块

| 模块 | 能力 |
|------|------|
| 租户管理 | 开通学校（复用 init-school 流程界面化）、租户状态、Schema 健康检查 |
| 订阅管理 | 录入/续约/变更订阅（关联合同号）、单校权益 override、试用转正式（design/21 衔接） |
| 用量监控 | 全租户用量总览、Top 消耗租户、异常用量告警（单日用量 > 均值 5 倍 → 疑似异常/滥用） |
| SLA 与健康 | 各租户可用性摘要（接 Prometheus 既有指标）、S0 预警处理时效达标率（脱敏聚合，不见内容） |
| 公告与通知 | 向指定租户教师端推送运营公告（版本更新/维护窗口） |
| 审计 | 平台侧操作全量审计（复用 audit 包模式：谁在何时改了哪个租户的订阅） |

### 6.2 数据边界（合规红线）

平台运营后台**只能访问 public schema 的平台级数据 + 聚合指标**：
- ✅ 可见：订阅、用量计数、SLA 指标、租户元数据
- ❌ 不可见：任何学生对话/画像/测评/预警内容（在租户 schema 内，平台角色无路由权限）——技术上通过数据源路由白名单强制，不靠约定

### 6.3 API 增量（/api/v1/platform/*，风格沿 design/16）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/platform/tenants/{id}/subscriptions` | 录入订阅 |
| PATCH | `/api/v1/platform/subscriptions/{id}` | 续约/变更/暂停 |
| PUT | `/api/v1/platform/subscriptions/{id}/overrides` | 单校权益定制 |
| GET | `/api/v1/platform/usage/overview?period=` | 全租户用量总览 |
| GET | `/api/v1/platform/plans` / `PATCH /plans/{id}` | 计划与权益矩阵维护 |
| POST | `/api/v1/platform/announcements` | 运营公告 |

## 七、实施里程碑与验收

| 阶段 | 范围 | 验收标准（EARS 摘要） |
|------|------|---------------------|
| M1 | plans/entitlements/subscriptions 模型 + EntitlementFilter（bool 权益）+ 豁免注解 | WHEN 基础版租户请求 parent_h5 接口 THEN 系统 SHALL 返回 403/30002；WHEN 任意订阅状态下触发 S0 THEN 预警链路 SHALL 完整执行 |
| M2 | 计量事件流 + quota 执行 + 429 头 + 阈值告警 + 学校用量视图 | WHEN 租户 TTS 用量达上限 THEN 后续合成请求 SHALL 429 且学生端 SHALL 静默降级纯文字；Redis 与 usage_events 日终对账差异 SHALL <0.1% |
| M3 | 订阅生命周期自动流转 + 平台运营后台六模块 | WHEN 订阅到期进入 grace THEN 教师端 SHALL 显示续费横幅且功能保留 30 天；WHEN 平台角色请求租户业务数据 THEN 数据源路由 SHALL 拒绝 |

**测试要点**：豁免清单全接口回归（断言危机链路在 expired/超额下可用）；配额并发竞争（Redis 原子性）用例；grace→expired 定时任务用例；平台角色越权访问租户 schema 的安全用例；金额精度——本期系统内无金额计算，`price_per_student_year` 仅展示字段，如未来引入 Rating 须遵循 code-finance-precision 规则（BigDecimal/分为单位）。
