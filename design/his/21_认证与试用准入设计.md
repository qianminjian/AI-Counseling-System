# 21 认证与试用准入设计

> 创建：2026-07-23 | 状态：设计待确认（4 个决策点需项目负责人拍板）| 关联：07 SaaS 多学校隔离、10 政策与合规、14 儿童安全对话规范、16 API 接口设计
> 核心：在产品发布公网试用前，设计**可兼容未来学校正式部署**的认证与试用准入方案，并增加**试用前告知同意流程**（未成年人合规底线）。
> ⚠️ 合规红线：本文涉及的未成年人数据保护、监护人同意、免责条款有效性等属监管责任事项（AGENTS.md §3.7），AI 只提供方案信息，**最终合规判断需项目负责人 + 法务审定**。
> ⚠️ **实现现状（2026-07-28 核对）**：本篇 P0/P1 已全部落地并超出（试用注册/同意留痕/chat 鉴权收紧/轮询+桌面通知/WebSocket/PIN 登录/首次强制改密均已实现 🟩）；§2 现状分析与§七集成点为 2026-07-23 快照已过时；租户隔离实态为行级非 Schema 级（见 07 §11）；四态对照见 §十一。

## 一、背景与目标

### 1.1 问题

当前系统（M1 核心闭环原型）若要发布到公网供公众试用，存在两个缺口：

1. **认证缺口**：学生端无登录界面（`frontend/student-h5/src/App.jsx` 直接进入情绪选择），`ChatController.createSession` 中学生 `userId`/`tenantId` **硬编码**，无法区分真实用户、无法隔离试用数据。
2. **合规缺口**：面向未成年人（10-12 岁小学生）的心理辅导产品，公网试用前缺少**产品性质告知 + 非危机声明 + 隐私告知 + 监护人同意**的准入流程，直接上线有合规风险。

### 1.2 目标

- **兼容**：试用认证方案不另起炉灶，复用现有 JWT 身份契约，未来学校正式部署（账号密码 / 微信 / 手机号）可平滑扩展。
- **可控**：试用准入可控制人群范围（邀请码）、可追溯（同意留痕）、可隔离（独立试用租户）。
- **合规**：试用前完成"告知 + 同意"，满足未成年人个人信息保护的形式要件（实质合规仍需安全措施 + 法务审定）。

### 1.3 非目标（YAGNI）

- 不做实名认证 / 人脸核身 / 身份证 OCR（MVP 试用不需要，且增加未成年人数据收集，违背最小化原则）。
- 不做完整的家长管理后台（M2+ 规划）。
- 不做微信 / 手机号 OAuth 接入（试用阶段用邀请码 + 昵称即可，正式部署再做）。

**方案 B（已确认）：临时密码 + 首次登录强制改密**
- Flyway 种子建 `minjianq`（`userType=psych_teacher`、`tenant=tenant_trial`、`status=active`），设**随机临时密码**（BCrypt 加密入库，明文临时密码写入种子文件/启动日志供项目负责人读取），`must_change_password=true`
- `minjianq` 用临时密码登录教师端 → `must_change_password=true` 时**强制跳转改密页**，不可访问其他功能
- 改密端点 `POST /api/v1/auth/change-password`：凭旧密码 + 新密码 → BCrypt 加密 → `must_change_password=false`
- 之后用 `minjianq` + 自设密码正常登录
- 优点：复用现有登录流程，最简单；缺点：种子含临时密码（随机生成，首次登录后即失效）

> 方案 A（setup token，无预置密码）为备选，未采用。

> **DB 影响**：`users` 表需加 `must_change_password BOOLEAN DEFAULT false` 标记字段，命中 DB schema 红线 #3，随 P0 迁移一并放行。临时密码生成与 `must_change_password` 强制改密逻辑需后端（`AuthController`/`TrialAuthService`）+ 教师端 `Login.jsx` 改密页配合。

## 四、统一身份契约（兼容核心）

### 4.1 JWT Claim 契约（保持不变，复用现有）

```
{
  "userId":   "UUID",      // 用户唯一标识
  "userType": "student",   // student | teacher | admin | trial_student
  "tenantId": "UUID",      // 租户（学校 / 试用租户）
  "iat": ..., "exp": ...
}
```

**兼容关键**：`userType` 增加 `trial_student` 枚举值，`tenantId` 指向**专用试用租户**。这样：
- 试用数据天然隔离在试用租户 Schema 内（复用 07 文档 Schema 级隔离）；
- 未来学校正式部署时，学生 `userType=student` + 学校 `tenantId`，**JWT 契约不变**，仅认证方式（策略）不同。

### 4.2 可插拔认证策略（开闭原则）

认证方式抽象为策略接口，试用 / 学校 / 微信 / 手机号都是不同实现，**新增认证方式不改动核心契约**：

```java
// counseling-api/.../auth/AuthStrategy.java（新增端口）
public interface AuthStrategy {
    /** 策略标识（trial / school / wechat / phone） */
    String type();
    /** 认证并返回统一身份；失败抛 BizException(UNAUTHORIZED) */
    AuthenticatedUser authenticate(AuthRequest request);
}

// AuthenticatedUser：统一身份载体（userId, userType, tenantId, pseudonym）
```

| 策略 | 触发场景 | 实现要点 | 阶段 |
|------|---------|---------|------|
| `TrialAuthStrategy` | 试用注册/登录 | 邀请码校验 + 昵称 + 年龄 + 同意记录 → 创建/查找 trial_student | **本期** |
| `SchoolPasswordAuthStrategy` | 学校正式部署 | 现有 `pseudonym + 密码`（即现 AuthController.login 逻辑迁入） | 现有 |
| `WechatAuthStrategy` | 微信登录 | OAuth code → openid → 绑定用户 | 正式期（YAGNI 暂不做） |
| `PhoneAuthStrategy` | 手机号验证码 | 短信验证码校验 | 正式期（YAGNI 暂不做） |

> 现有 `AuthController.login` 的密码逻辑即 `SchoolPasswordAuthStrategy` 的雏形，本期不重构它，仅新增 `TrialAuthStrategy`，保持精准修改。

## 五、试用准入流程

### 5.1 端到端流程（D1=A 成人体验者 / D2=邀请码 / D3=邀请码+昵称+年龄）

```
[输入邀请码] → [校验有效] → [填写昵称 + 年龄 + 角色]
   → [年龄判断]
       ├─ <14 岁 → 触发监护人同意流程（§6.3）→ [监护人手机号 + 同意]
       └─ ≥14 岁 / 成人 → [本人告知同意 §6.2]
   → [勾选知情同意 + 留痕]
   → [创建 trial_student 用户 + 试用租户]
   → [签发 JWT] → [进入情绪选择 → 对话]
```

### 5.2 试用注册端点（新增 API）

```
POST /api/v1/auth/trial/register
Request:
{
  "inviteCode":  "string",   // 必填，邀请码
  "pseudonym":   "string",   // 必填，昵称（2-12 字，不收集真实姓名）
  "age":         int,        // 必填，年龄（用于判断是否需监护人同意）
  "role":        "string",   // 可选，体验者身份（家长/老师/其他）
  "consentVersion": "string",// 必填，同意的告知同意版本号
  "guardianPhone": "string"  // age<14 时必填（监护人手机号，脱敏存储）
}
Response: { token, userId, tenantId, userType:"trial_student" }
```

校验规则：
- 邀请码：存在、未过期、未超使用次数上限；
- 昵称：长度 2-12，过滤敏感词（复用 `SafetyKeywordLibrary` 思路或简单黑名单）；
- 年龄：<10 岁提示"建议在家长陪同下使用"；<14 岁强制监护人同意；
- `consentVersion` 必须匹配当前生效版本（防伪造旧版本同意）。

### 5.3 邀请码管理（轻量）

- 复用现有表或新增 `trial_invite_codes`（code, max_uses, used_count, expires_at, status）；
- 由管理员手动生成发放（MVP 不做自助申请审批流）。

### 5.4 试用租户隔离

- 预置一个**专用试用租户** `tenant_trial`（固定 tenantId），所有试用用户 `tenantId` 指向它；
- 试用数据天然落在 `tenant_trial` Schema，与未来真实学校租户物理隔离；
- 试用租户可配置：风险通知接收人 = "试用咨询师"（D4=A）。

## 六、告知同意流程（合规底线）

> **核心判断**：要加，但定位必须是"**告知 + 同意**"而非"免责金牌"。
> - 免责声明 ≠ 免责：对未成年人的保护责任是法定义务，不能靠一纸声明免除；
> - 过度免责的格式条款无效（《民法典》第 497 条）；
> - 真正的保护来自**实质安全措施 + 合规 + 诚实定位**，告知同意是形式要件 + 用户知情权保障。

### 6.1 告知同意内容框架（门控页，进入产品前强制展示）

| 模块 | 必含内容 | 依据 |
|------|---------|------|
| **产品性质声明** | 本产品是 AI 情绪陪伴助手，**非医疗服务、非专业心理咨询**，不能诊断、不能开药、不能替代面对面咨询 | 诚实定位，避免误导 |
| **非危机声明 + 危机资源** | "如果你或孩子正处于危机中，请立即拨打 24h 心理援助热线 **400-161-9995** 或 120/110，本工具不适合处理紧急情况" | design/14 §5 危机资源（热线号码与代码 `OutputContentFilter.CRISIS_HOTLINE` 一致） |
| **隐私告知** | 收集哪些数据（昵称/年龄/对话内容）、用途（提供陪伴 + 风险识别）、存储（国内云、加密）、保留期限、可删除 | PIPL 第17条告知义务 |
| **AI 局限性告知** | AI 可能出错、可能无法识别所有风险、回复仅供参考 | 生成式 AI 暂行办法 |
| **监护人同意**（未成年人） | 不满 14 周岁需监护人单独同意处理其个人信息 | PIPL 第31条 |
| **年龄门槛** | 建议 10-12 岁在家长陪同下使用 | 产品定位 |
| **服务条款** | 使用规范、禁止行为、责任边界（**措辞需法务审定**，完整条款见 [22_告知同意条款.md](22_告知同意条款.md)） | 民法典 496-497 |

### 6.2 呈现形式

- **门控页（Gate Page）**：进入产品前全屏展示，必须滚动到底 + 勾选"我已阅读并同意"才能继续；
- **分层呈现**：首屏关键信息（非医疗 + 危机热线 + 隐私要点），详情可展开/链接到完整条款；
- **儿童 vs 监护人区分**：
  - 成人体验者（D1=A）：本人同意即可；
  - 真实未成年人（D1=B 或 age<14）：增加监护人手机号 + 监护人同意确认（MVP 可用"监护人手机号 + 短信/勾选确认"，正式期做实名验证）。

### 6.3 同意留痕（数据设计）

同意记录**版本化**入审计（复用 `audit_logs` 或新增 `consent_records`）：

```sql
-- 复用/新增同意记录表（无敏感字段，仅留痕）
CREATE TABLE consent_records (
  consent_id     UUID PRIMARY KEY,
  user_id        UUID NOT NULL,
  tenant_id      UUID NOT NULL,
  consent_type   VARCHAR(32),   -- trial_terms / guardian_consent / privacy_policy
  consent_version VARCHAR(16),  -- 告知同意版本号（如 v1.0）
  consented_at   TIMESTAMP,
  ip_hash        VARCHAR(64),   -- 来源 IP 哈希（审计用，脱敏）
  user_agent     VARCHAR(255)
);
```

- 每次告知同意版本升级，需用户重新同意（旧记录保留，不覆盖）；
- 同意版本号写入 JWT 或用户档案，便于校验"是否已同意当前版本"。
