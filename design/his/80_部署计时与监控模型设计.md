## §1 背景与目标

### 1.1 现状摩擦点

| # | 摩擦点 | 活证据 |
|---|--------|--------|
| F1 | deploy.sh 无步骤耗时统计，部署耗时变化不可见 | 服务器 Maven 打包 400s 是常态还是变坏？无基线无法回答；doing/72 全量 36min 教训只能靠记忆 |
| F2 | 无部署日志留存，排障依赖终端输出 | 终端滚动丢失后无法回看步骤上下文；今日冒烟 4 项根因排查靠 ssh 翻 docker logs |
| F3 | 无历史基线 → 无法回答「这次比平时慢吗」 | 阈值判定无数据支撑，全靠人工经验 |
| F4 | 失败排查靠人肉翻日志 | 今日 4 项冒烟失败根因（20003 同意闭环/personas 白名单/路由 404/JSON 500）均为可固化的失败模式 |

### 1.2 目标（DOC-077）

1. **步骤计时**：deploy.sh 关键步骤自动计时（毫秒级），部署总耗时统计
2. **固定格式汇报**：部署完成输出结构化汇报（组件/结果/总耗时/步骤明细/信号/建议）
3. **日志**：`logs/deploy/deploy-<ts>.log` 持久化（含结构化统计段），`.deploy-state` 扩展统计快照
4. **监控模型**：历史基线 → 阈值判定（绝对 + 相对）→ 变坏分析（步骤级偏差 + 原因映射）→ 信号分级（OK/WARN/CRITICAL）
5. **自动修复完善**：轻量自愈动作（幂等安全）+ 失败模式知识库自动输出修复指引

### 1.3 范围边界（YAGNI，不做）

- ❌ 远端监控服务/仪表盘（frozen/40 水平扩展阶段再议）
- ❌ 部署耗时趋势图/可视化（日志数据积累足够后再议）
- ❌ 失败自动回滚（红线：发布审批人工；回滚走既有 `--rollback` 通道）
- ❌ 步骤耗时上报远端（本地基线足够当前单机部署形态）

## §2 方案设计

### 2.1 部署步骤清单（计时点）

| key | 中文名 | 绝对阈值(秒) | 阈值依据 |
|-----|--------|-------------|---------|
| precheck | 前置检查 | 60 | 本地 git/flyway 校验 |
| detect | 变更检测 | 10 | git diff 本地操作 |
| compile-backend | 后端预检编译 | 300 | 本地 Maven 增量编译实测 ~10s，全量冷启动 3-5min |
| prepare-models | 模型投放 | 600 | 109M 模型 + hf-mirror 波动（实测 ~2min，首次/网络差更久） |
| build-student | 学生端构建 | 240 | vite 实测 ~1s（增量），全量含模型复制 |
| build-teacher | 教师端构建 | 240 | tsc + vite 实测 ~30s |
| build-parent | 家长端构建 | 240 | taro 构建较重 |
| rsync | 源码同步 | 600 | 3Mbps 上行（doing/72 教训），增量小、全量大 |
| build-images | 镜像构建 | 1500 | 服务器 Maven 打包实测 400s + 依赖下载（首次 10min+） |
| restart | 服务重启 | 300 | voice 模型加载慢（实测 ~40s） |
| smoke | 发布后置冒烟 | 900 | SSE 真实对话多轮 + 风险链路（DA-04） |
| nginx-check | nginx 路径校验 | 60 | ssh 校验 + retry |

说明：
- 绝对阈值 = 「明显异常」下界（常态耗时应在阈值内）；相对阈值（§2.4）用于更敏感地捕获漂移。
- 步骤按实际部署组件动态出现（`--backend` 只计时 backend 相关步骤），未执行的步骤不计时不计判。

### 2.2 计时与日志机制

- **计时**：`dm_start <key>` / `dm_end <key>`，毫秒取时用 `python3 -c 'import time;print(int(time.time()*1000))'`（macOS `date` 无 `%N`；python3 为本地既有依赖，smoke-test.sh 已用）。
- **日志**：脚本开头 `mkdir -p logs/deploy`，`exec > >(tee -a "$LOG_FILE") 2>&1`（bash 进程替换，macOS bash 3.2 支持）；`LOG_FILE=logs/deploy/deploy-<YYYYmmdd-HHMMSS>.log`。
- **结构化统计段**（追加日志末尾，供基线解析）：
  ```
  # deploy-metrics v1
  deploy_result=SUCCESS|FAILED
  deploy_components=backend student ...
  deploy_duration_ms=<总耗时>
  step_<key>_ms=<各步骤耗时>
  signal=OK|WARN|CRITICAL
  signal_details=<WARN/CRITICAL 步骤摘要，OK 为空>
  ```
- **`.deploy-state` 扩展**（部署成功时追加）：`LAST_DEPLOY_DURATION_MS`、`LAST_DEPLOY_SIGNAL`、`LAST_STEP_<KEY>_MS`，供快速对比与日志外快速查看。
- **`.gitignore`**：追加 `logs/deploy/`（运行时产物不入库；基线丢失可重新积累，文档说明）。
- **编排出口 `dm_finish_deploy`**（库内函数，deploy.sh `trap EXIT` 调用）：补 end 未完成步骤（失败时最后未完成者即失败步骤）→ 总耗时 → 汇报 → 统计段 → `.deploy-state` 快照；`DM_IN_FLOW=1`（进入部署流程）才输出汇报，门禁拦截保持快速失败。

### 2.3 固定格式汇报

部署结束（成功或失败）统一输出：

```
================================================
📦 MindSafe 部署汇报（DOC-077 监控模型）
================================================
组件   : backend student teacher parent tts voice
结果   : ✅ SUCCESS（冒烟 32/32 通过） | ❌ FAILED（<失败步骤>）
总耗时 : 12m 34s
┌ 步骤耗时明细 ──────────────────────────────
│ 前置检查      2.1s ▏
│ 后端预检编译  8.5s ▇▇
│ 镜像构建    408.5s ▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇
└─────────────────────────────────────────────
信号   : 🟢 OK / 🟡 WARN（<步骤> 超阈值）/ 🔴 CRITICAL（<步骤>）
建议   : <WARN/CRITICAL 时输出修复建议，OK 为空>
日志   : logs/deploy/deploy-20260808-133000.log
================================================
```

- 条形图比例 = 步骤耗时 / 总耗时 × 20 字符，最少 1 格。
- bash 3.2 兼容：所有变量 `${var}` 包裹（2026-08-07 全角字符丢字节教训，deploy.sh 注释已固化），条形图字符不与变量直接相邻。

### 2.4 监控模型（变坏判定）

**基线构建**（`dm_baseline <step>`）：
- 数据源：`logs/deploy/deploy-*.log` 中 `step_<key>_ms=` 行，取最近 10 次
- 统计量：mean / p90（样本 ≥3 时排序取 90 分位；<3 时用 max 替代）/ max
- 无历史 → 无基线（仅绝对阈值判定）

**阈值判定**（每步骤）：
- 无基线：耗时 > 绝对阈值 → WARN；> 2× 绝对阈值 → CRITICAL
- 有基线：耗时 > max(p90×1.5, 绝对阈值) → WARN；> max(p90×2, 绝对阈值×2) → CRITICAL

**变坏分析**（超阈值步骤输出）：
- 本次耗时 vs 基线 mean/p90 + 偏差倍数
- 原因映射表（步骤 → 可能原因 → 建议动作）：

| 步骤 | 可能原因 | 建议动作 |
|------|---------|---------|
| compile-backend | 本地机器负载 / 依赖变更冷启动 | 检查本机 CPU 负载与 mvn 日志 |
| prepare-models | hf-mirror 网络波动 | 重跑 deploy.sh（模型已下载部分跳过） |
| build-* | 本地负载 / 依赖升级首装 | 检查本机负载；依赖变更属预期 |
| rsync | 本机上行带宽受限（3Mbps 教训 doing/72） | 检查带宽；增量部署应小于 10MB |
| build-images | 服务器 CPU/网络/磁盘 / Maven 依赖下载 | 查看 docker compose build 日志；磁盘 df -h |
| restart | voice 模型加载慢 / 容器异常 | service-manager status 查看 |
| smoke | LLM 响应变慢 / TTS 服务异常 | 查看后端日志 LLM 延迟与 tts-service |

**信号分级**：存在 CRITICAL 步骤 → CRITICAL；存在 WARN 步骤 → WARN；否则 OK；部署失败 → FAILED（信号=CRITICAL，结果字段区分）。

### 2.5 自动修复完善（安全边界内）

| 层级 | 机制 | 说明 |
|------|------|------|
| L1 已有 | retry 执行器 | rsync/build/ssh 网络类自动重试（3 次，退避） |
| L2 新增 | rsync 降速自愈 | 首次失败重试自动加 `--bwlimit=4096`（3Mbps 带宽实测） |
| L3 新增 | 构建缓存清理自愈 | build-images 首次失败 → 自动 `docker builder prune -f` 清缓存后重试（幂等、无业务风险） |
| L4 新增 | 失败模式知识库 | 部署失败时按特征自动输出修复指引（见 §2.6） |

**失败模式知识库**（FAILED 时特征匹配输出）：

| 特征（日志 grep） | 根因 | 修复指引 |
|------------------|------|---------|
| `code=20003` + smoke 失败 | 注册年龄 <14 + `trial-auto-grant=false`（生产 SMS 闭环） | 冒烟注册改 age≥14，或实现 SMS 确认闭环 |
| `error TS2741` | 组件 props 必填缺参 | 检查报错组件调用处补参或设缺省 |
| `NoResourceFoundException` | API 路由不存在 | 核对冒烟路径与真实路由（如 emotion-diary → diary/history） |
| `/tts/personas` 403 | SecurityConfig 白名单遗漏 | 补 permitAll 白名单 |
| `URI is not absolute` | WeCom webhook 配置缺失/格式错 | 检查企微告警 webhook 环境变量 |
| `HttpMessageNotReadableException` 500 | 全局异常处理缺映射 | 补 400 映射 |

**红线确认**：自动修复仅限幂等安全动作（降速重试/清缓存），不做自动回滚、不做自动发布审批。

**关键实现决策**：
- 计时与判定逻辑全部放独立库 `deploy-metrics.sh`（SRP + 可测试性——shell 测试可直接 source 库函数，不必 mock 整个 deploy.sh）
- 编排函数 `dm_finish_deploy` 也入库（T11/T12 可测），deploy.sh 仅留 `trap 'dm_finish_deploy $? ...' EXIT` 注册——失败路径也输出汇报与统计段（今日冒烟失败无统计的教训）
- 库内全部管道/条件赋值用 if 或 `|| true` 包裹（`set -eo pipefail` 下 grep 无匹配返回 1 会误触发退出，部署首跑无基线时必现）
- 汇报条数与断言数兼容：冒烟段已输出「E2E 冒烟测试通过：32/32」，汇报中复用该信息

## §4 验收标准（测试断言）

`tests/unit/scripts/deploy-metrics-test.sh`（shell 测试，纳入 CI 七件套）：

| # | 用例 | 断言 |
|---|------|------|
| T1 | dm_start/dm_end 计时 | 模拟 1.2s 步骤，`dm_end` 后耗时 ≥1000ms 且 <3000ms |
| T2 | 未 start 直接 end | 报错退出（防误用） |
| T3 | 无基线判定 | 耗时 > 绝对阈值 → WARN；> 2× → CRITICAL；正常 → OK |
| T4 | 有基线判定 | 构造 5 次历史基线，超 p90×1.5 → WARN；超 p90×2 → CRITICAL |
| T5 | 基线样本 <3 | 用 max 替代 p90，不报错 |
| T6 | 汇报格式 | 输出含「部署汇报」「组件」「结果」「总耗时」「信号」「日志」关键行 |
| T7 | 条形图 | 比例正确（最大步骤满格，最小步骤 ≥1 格） |
| T8 | 失败模式知识库 | 构造含 `code=20003` 的日志 → 输出监护人同意指引；构造 `TS2741` → 输出 props 指引 |
| T9 | 日志结构化段 | 统计段含 `deploy_result=` / `step_*_ms=` / `signal=` |
| T10 | 失败路径汇报 | 模拟失败（dm_report 前标记 result=FAILED）→ 汇报含 FAILED 与修复指引区 |
| T11 | 编排成功路径 | dm_finish_deploy：统计段写日志、快照落盘、dm_baseline 可解析日志 |
| T12 | 编排失败路径 | 未完成步骤 → fail_step 推导 + 信号 CRITICAL + 不写快照 |

**部署级验收**（下次真实部署）：
- 部署输出含固定格式汇报与步骤明细
- `logs/deploy/` 生成日志且可被基线解析
- 冒烟 32/32 保持通过
