## 1. 整体技术架构（分层）

系统采用分层架构，从前端到基础设施共 7 层，层间通过标准化接口通信。

| 层次 | 职责 | 技术方案（现行 Java 路线） |
|------|------|------|
| 前端层 | Web / H5 / 平板多端适配 | React 18 + TypeScript + Vite + Tailwind CSS |
| 负载均衡层 | 流量分发与健康检查 | Nginx / 云 SLB |
| API 网关层 | 统一入口、鉴权、限流 | Spring Cloud Gateway（或 APISIX） |
| 应用服务层 | 业务逻辑处理 | **Spring Boot 3 模块化单体（Maven 多模块）** |
| AI 编排层 | LLM 对话、RAG、Agent 编排、情绪识别 | **Spring AI（ChatClient + Advisors）** |
| 数据层 | 关系型/缓存/向量/文件存储 | PostgreSQL 16 + pgvector / Redis 7 / OSS |
| 基础设施层 | 计算、存储、网络 | Docker Compose（试点）/ Kubernetes（规模化） |

## 2. 前端架构

多端统一开发方案，支持 Web、H5、平板，使用统一业务逻辑和 UI 组件库。

| 架构要素 | 技术方案 | 说明 |
|------|------|------|
| 技术栈 | React 18 + TypeScript + Vite | 类型安全，快速构建 |
| 组件库 | Ant Design / Ant Design Mobile | 企业级 UI，开箱即用 |
| 状态管理 | Zustand | 轻量简洁，复杂场景可升级 Redux Toolkit |
| 路由 | React Router v6 | 嵌套路由、懒加载 |
| 响应式 | Tailwind CSS + Flex/Grid | 多端适配 |
| 包管理 | pnpm | 依赖高效、磁盘占用低 |

**特点**：组件化开发、全局/本地状态分离、路由懒加载首屏优化、Tailwind 多端适配、PWA 离线缓存。

## 3. 后端架构（模块化单体，决策 #8）

后端采用**模块化单体（Modular Monolith）**，用 Maven 多模块按业务域拆分包边界，而非独立部署的微服务——在试点阶段以更低的运维成本获得清晰的模块边界，未来可按模块演进为服务。

### 3.1 后端技术选型

| 架构要素 | 技术方案 | 说明 |
|------|------|------|
| 语言/运行时 | Java 21（虚拟线程） | 高并发 I/O 场景低成本 |
| 框架 | Spring Boot 3 | 生态成熟，Spring AI 原生集成 |
| 持久层 | MyBatis-Plus | SQL 可控，多租户拦截器友好 |
| API 规范 | OpenAPI 3.0 / SpringDoc | 自动文档 |
| 消息/异步 | Spring Events（进程内）/ Redis 队列 | 解耦，试点期不引入 Kafka |
| 构建 | Maven | 多模块管理 |

### 3.2 Maven 多模块结构

```
backend/
├── counseling-common/    通用工具、异常、返回体、常量
├── counseling-tenant/    多租户（AbstractRoutingDataSource、TenantContextFilter）
├── counseling-domain/    领域模型、MyBatis Mapper、DO/Entity
├── counseling-ai/        AI 编排（Spring AI、7 Agent、CBT 状态机、RAG、Advisor 链）
├── counseling-service/   业务服务（预警、个案、测评、预约、协同、报表）
├── counseling-api/       Web 层（Controller、Spring Security + JWT）
└── counseling-app/       启动模块（装配、配置、Main）
```

依赖方向：`api → service → domain → common`；`ai` 被 `service` 依赖；`tenant` 被 `domain/service` 依赖。禁止反向依赖。

### 3.3 业务域划分（模块内包边界）

用户与权限、咨询会话、AI 能力、知识库、测评、预警与个案、通知——各域在 `counseling-service` 内独立分包，通过接口交互，为未来拆分预留边界。

## 4. AI 编排架构（Spring AI，决策 #9）

AI 层是系统核心能力层。采用 **Spring AI** 统一抽象 LLM 调用与 Advisor 链，替代原文的 LangChain/vLLM 方案。详细工作流见 13 文档。

### 4.1 LLM 编排层

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 模型调用 | Spring AI `ChatClient` | 统一抽象层，LLM 供应商无关（决策 #7） |
| 供应商适配 | 主备多 Provider + 降级 | 主模型故障降级备用模型/轻量模型/规则兜底 |
| Prompt 管理 | `PromptTemplate` 资源 + 版本管理 | 支持 A/B 测试、快速回滚（见 02 文档） |
| 缓存策略 | Redis + 相似 Prompt 缓存 | 降低延迟与成本 |
| 编排 | Advisor 链 + 状态机 | 替代 LangGraph，见 13 文档 |

### 4.2 Advisor 链（安全控制核心）

```
SafetyInputAdvisor        （输入安全检测，最先执行）
→ MemoryAdvisor(读)       （会话记忆）
→ QuestionAnswerAdvisor    （RAG 检索，pgvector）
→ LLM 生成
→ SafetyOutputAdvisor      （输出审查/改写/阻断/升级）
→ MemoryAdvisor(写)
→ LoggingAdvisor           （审计日志）
```

> Advisor 的 `getOrder()` 必须保证安全 Advisor 的前置/后置铁律，安全检测不可被绕过。

### 4.3 情绪识别与语音（分期）

- **文本情绪分析**（一期）：通过 Spring AI 调用分类能力，输出主情绪/强度/置信度（Emotion Agent，见 13 文档）。
- **语音 ASR/TTS、多模态融合**（二期起）：作为外部能力通过供应商无关接口接入，一期不纳入（YAGNI，与 05/08 MVP 边界一致）。

## 5. 数据架构

数据层采用多模态存储，按数据特性选择存储引擎。

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 主数据库 | PostgreSQL 16 + 主从复制 | 读写分离，Schema 级多租户（见 06/07） |
| 缓存 | Redis 7（Cluster + Sentinel） | 会话缓存、限流、分布式锁 |
| 向量库 | **pgvector** | 与主库同实例，简化架构（不引入 Milvus） |
| 文件存储 | 阿里 OSS / 腾讯 COS | CDN 加速，租户隔离 Bucket |

### 5.1 向量检索（pgvector）

- 向量维度：按所选 embedding 模型确定（供应商无关）
- 索引类型：HNSW / IVFFlat，平衡精度与性能
- 相似度：Cosine Similarity
- 检索方式：混合检索（向量 + 关键词），仅检索经审核的知识库（见 15 文档）

## 6. 部署架构

- **试点阶段**：Docker Compose 单机编排（应用 + PostgreSQL + Redis），降低运维门槛，与模块化单体匹配。
- **规模化阶段**：Kubernetes 编排，弹性伸缩、高可用。
- **私有化部署**：All-in-One（≤500 人）/ 分离部署 / 容器化，见 07 文档。
- **CI/CD**：代码提交 → 构建 → 单元测试 → 镜像构建 → 推送仓库 → 部署（集成测试 → 金丝雀 → 全量）。

## 7. 安全架构

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 身份认证 | JWT + OAuth2.0（钉钉/企微登录） | 见 07 文档 SSO |
| 传输加密 | TLS 1.2+ | 全链路 HTTPS，内部 mTLS |
| 存储加密 | AES-256 + KMS/Vault 密钥管理 | 敏感字段加密，密钥轮换 |
| 网络安全 | 防火墙 + DDoS 防护 + WAF | 防 SQL 注入、XSS |
| 脱敏 | 日志/监控自动脱敏 | 防敏感信息泄露 |

## 8. 监控运维架构

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 日志收集 | ELK / 轻量 Loki（试点） | 集中日志，快速检索 |
| 指标监控 | Prometheus + Grafana（Micrometer 埋点） | 自定义看板、告警 |
| 链路追踪 | OpenTelemetry + Jaeger | 分布式追踪 |
| 告警 | AlertManager + 钉钉/企微通知 | 多级告警 |

Spring Boot Actuator + Micrometer 原生暴露指标；日志冷数据归档 OSS 降本；TraceID 串联请求全链路。

## 9. 技术选型总结表（现行 Java 路线）

| 组件类别 | 技术选型 | 选型理由 |
|------|------|------|
| 前端框架 | React 18 + TypeScript | 生态完善、组件丰富 |
| 后端框架 | Java 21 + Spring Boot 3 | 生态成熟，Spring AI 原生集成，团队可维护 |
| 架构风格 | 模块化单体（Maven 多模块） | 试点期运维成本低，模块边界清晰（决策 #8） |
| 持久层 | MyBatis-Plus | SQL 可控，多租户拦截器友好 |
| API 网关 | Spring Cloud Gateway | 与 Spring 生态一致 |
| 数据库 | PostgreSQL 16 | 功能丰富、支持 JSON、pgvector 向量化 |
| 缓存 | Redis 7 | 高性能、多数据结构 |
| 向量库 | pgvector | 与主库同实例，简化架构（决策 #7） |
| AI 编排 | Spring AI | 供应商无关、Advisor 链、替代 LangChain（决策 #9） |
| 容器编排 | Docker Compose → Kubernetes | 分阶段演进 |
| 监控 | Prometheus + Grafana | 云原生标准 |
| 链路追踪 | OpenTelemetry + Jaeger | 分布式追踪 |
| 对象存储 | 阿里 OSS / 腾讯 COS | 稳定、CDN 加速 |
