## 1. 整体技术架构（分层）

系统采用分层架构，从前端到基础设施共 7 层，层间通过标准化接口通信。

| 层次 | 职责 | 技术方案（现行 Java 路线） |
|------|------|------|
| 前端层 | Web / H5 / 平板多端适配 | React 18 + TypeScript + Vite + Tailwind CSS |
| 负载均衡层 | 流量分发与健康检查 | Nginx / 云 SLB |
| API 网关层 | 统一入口、鉴权、限流 | Spring Cloud Gateway（或 APISIX） |
| 应用服务层 | 业务逻辑处理 | **Spring Boot 3 模块化单体（Maven 多模块）** |
| AI 编排层 | LLM 对话、RAG、Agent 编排、情绪识别 | **Spring AI（ChatClient + Advisors）** |
| 数据层 | 关系型/缓存/向量/文件存储 | PostgreSQL 16 + pgvector / Redis 7 / OSS |
| 基础设施层 | 计算、存储、网络 | Docker Compose（试点）/ Kubernetes（规模化） |

## 2. 前端架构

多端统一开发方案，支持 Web、H5、平板，使用统一业务逻辑和 UI 组件库。

| 架构要素 | 技术方案 | 说明 |
|------|------|------|
| 技术栈 | React 18 + TypeScript + Vite | 类型安全，快速构建 |
| 组件库 | Ant Design / Ant Design Mobile | 企业级 UI，开箱即用 |
| 状态管理 | Zustand | 轻量简洁，复杂场景可升级 Redux Toolkit |
| 路由 | React Router v6 | 嵌套路由、懒加载 |
| 响应式 | Tailwind CSS + Flex/Grid | 多端适配 |
| 包管理 | pnpm | 依赖高效、磁盘占用低 |

**特点**：组件化开发、全局/本地状态分离、路由懒加载首屏优化、Tailwind 多端适配、PWA 离线缓存。

## 3. 后端架构（模块化单体，决策 #8）

后端采用**模块化单体（Modular Monolith）**，用 Maven 多模块按业务域拆分包边界，而非独立部署的微服务——在试点阶段以更低的运维成本获得清晰的模块边界，未来可按模块演进为服务。

### 3.1 后端技术选型

| 架构要素 | 技术方案 | 说明 |
|------|------|------|
| 语言/运行时 | Java 21（虚拟线程） | 高并发 I/O 场景低成本 |
| 框架 | Spring Boot 3 | 生态成熟，Spring AI 原生集成 |
| 持久层 | MyBatis-Plus | SQL 可控，多租户拦截器友好 |
| API 规范 | OpenAPI 3.0 / SpringDoc | 自动文档 |
| 消息/异步 | Spring Events（进程内）/ Redis 队列 | 解耦，试点期不引入 Kafka |
| 构建 | Maven | 多模块管理 |

### 3.2 Maven 多模块结构

```
backend/
├── counseling-common/    通用工具、异常、返回体、常量
├── counseling-tenant/    多租户（AbstractRoutingDataSource、TenantContextFilter）
├── counseling-domain/    领域模型、MyBatis Mapper、DO/Entity
├── counseling-ai/        AI 编排（Spring AI、7 Agent、CBT 状态机、RAG、Advisor 链）
├── counseling-service/   业务服务（预警、个案、测评、预约、协同、报表）
├── counseling-api/       Web 层（Controller、Spring Security + JWT）
└── counseling-app/       启动模块（装配、配置、Main）
```

依赖方向：`api → service → domain → common`；`ai` 被 `service` 依赖；`tenant` 被 `domain/service` 依赖。禁止反向依赖。

### 3.3 业务域划分（模块内包边界）

用户与权限、咨询会话、AI 能力、知识库、测评、预警与个案、通知——各域在 `counseling-service` 内独立分包，通过接口交互，为未来拆分预留边界。

## 4. AI 编排架构（Spring AI，决策 #9）

AI 层是系统核心能力层。采用 **Spring AI** 统一抽象 LLM 调用与 Advisor 链，替代原文的 LangChain/vLLM 方案。详细工作流见 13 文档。

### 4.1 LLM 编排层

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 模型调用 | Spring AI `ChatClient` | 统一抽象层，LLM 供应商无关（决策 #7） |
| 供应商适配 | 主备多 Provider + 降级 | 主模型故障降级备用模型/轻量模型/规则兜底 |
| Prompt 管理 | `PromptTemplate` 资源 + 版本管理 | 支持 A/B 测试、快速回滚（见 02 文档） |
| 缓存策略 | Redis + 相似 Prompt 缓存 | 降低延迟与成本 |
| 编排 | Advisor 链 + 状态机 | 替代 LangGraph，见 13 文档 |

> ✅ **实现状态（2026-08-01 核对）**：
> - **主备降级**：`ResilientChatModel` 装饰器已实现（主 DeepSeek → 备 qwen-plus），主模型异常时自动切换，对应配置 `mindsafe.ai.fallback.*`。
> - **流式增强**：`LlmStreamEnhancer` 已实现（PERF-001/002）——首 token 超时 12s（prod）/ 整体流超时 45s / 瞬时失败重试 1 次（2s 退避）/ 超时降级安全话术。Supplier 模式确保重试时创建全新 LLM 调用。
> - **TTS 合成**：`TtsService.synthesize()` + `/api/v1/tts/synthesize` 端点，返回完整音频二进制。
> - **性能监控**：Micrometer 自定义指标已埋点（`mindsafe.llm.*` / `mindsafe.tts.*`），Grafana Dashboard 自动加载（`deploy/monitoring/grafana/provisioning/dashboards/llm-performance.json`）。

### 4.2 Advisor 链（安全控制核心）

> ⚠️ **实现状态（2026-07-23 核对）**：下方为目标设计的完整 Advisor 链。M1 实际以 Service 层显式调用实现安全管线（输入 `RiskDetectorServiceImpl`+`PiiDesensitizer`，输出 `OutputContentFilter`+`OutputReviewService`），未采用 Advisor 链编排。已实现范围以 `design/04` §十七 为准。

```
SafetyInputAdvisor        （输入安全检测，最先执行）
→ MemoryAdvisor(读)       （会话记忆）
→ QuestionAnswerAdvisor    （RAG 检索，pgvector）
→ LLM 生成
→ SafetyOutputAdvisor      （输出审查/改写/阻断/升级）
→ MemoryAdvisor(写)
→ LoggingAdvisor           （审计日志）
```

> Advisor 的 `getOrder()` 必须保证安全 Advisor 的前置/后置铁律，安全检测不可被绕过。

### 4.3 情绪识别与语音（分期）

- **文本情绪分析**（一期）：通过 Spring AI 调用分类能力，输出主情绪/强度/置信度（Emotion Agent，见 13 文档）。
- **语音 ASR/TTS、多模态融合**（二期起）：作为外部能力通过供应商无关接口接入，一期不纳入（YAGNI，与 05/08 MVP 边界一致）。

## 5. 数据架构

数据层采用多模态存储，按数据特性选择存储引擎。

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 主数据库 | PostgreSQL 16 + 主从复制 | 读写分离，Schema 级多租户（见 06/07） |
| 缓存 | Redis 7（Cluster + Sentinel） | 会话缓存、限流、分布式锁 |
| 向量库 | **pgvector** | 与主库同实例，简化架构（不引入 Milvus） |
| 文件存储 | 阿里 OSS / 腾讯 COS | CDN 加速，租户隔离 Bucket |

### 5.1 向量检索（pgvector）

- 向量维度：按所选 embedding 模型确定（供应商无关）
- 索引类型：HNSW / IVFFlat，平衡精度与性能
- 相似度：Cosine Similarity
- 检索方式：混合检索（向量 + 关键词），仅检索经审核的知识库（见 15 文档）

## 6. 部署架构

- **试点阶段**：Docker Compose 单机编排（应用 + PostgreSQL + Redis），降低运维门槛，与模块化单体匹配。
- **规模化阶段**：Kubernetes 编排，弹性伸缩、高可用。
- **私有化部署**：All-in-One（≤500 人）/ 分离部署 / 容器化，见 07 文档。
- **CI/CD**：代码提交 → 构建 → 单元测试 → 镜像构建 → 推送仓库 → 部署（集成测试 → 金丝雀 → 全量）。

## 7. 安全架构

| 模块 | 技术方案 | 说明 |
|------|------|------|
| 身份认证 | JWT + OAuth2.0（钉钉/企微登录） | 见 07 文档 SSO |
| 传输加密 | TLS 1.2+ | 全链路 HTTPS，内部 mTLS |
| 存储加密 | AES-256 + KMS/Vault 密钥管理 | 敏感字段加密，密钥轮换 |
| 网络安全 | 防火墙 + DDoS 防护 + WAF | 防 SQL 注入、XSS |
| 脱敏 | 日志/监控自动脱敏 | 防敏感信息泄露 |

## 10. 模块依赖与包边界

### 10.1 Maven 模块依赖图

```
counseling-app (启动装配)
  └── counseling-api (Web 层)
        ├── counseling-service (业务服务)
        │     ├── counseling-ai (AI 编排)
        │     │     └── counseling-domain (领域模型)
        │     │           └── counseling-common (通用)
        │     └── counseling-domain
        └── counseling-tenant (多租户，被 domain/service 依赖)
```

**依赖铁律**：上层可依赖下层，下层不可依赖上层。`counseling-ai` 不依赖 `counseling-service`（通过接口回调用）。

### 10.2 模块职责与包结构

| 模块 | 核心包 | 职责 | 对外接口 |
|------|------|------|------|
| `counseling-common` | `.exception` `.dto` `.util` `.constant` | 统一异常、返回体、工具类、常量 | `Result<T>` / `BizException` |
| `counseling-tenant` | `.filter` `.context` `.interceptor` `.datasource` | TenantContext 绑定/清理、Schema 切换 | `TenantContextFilter` / `@CrossTenant` |
| `counseling-domain` | `.{domain}.mapper` `.{domain}.entity` `.{domain}.enums` | DO/Entity、MyBatis Mapper、枚举 | Mapper 接口 |
| `counseling-ai` | `.advisor` `.agent` `.state` `.prompt` `.rag` | Advisor 链、7 Agent、CBT 状态机、RAG | `ConversationOrchestrator` 接口 |
| `counseling-service` | `.alert` `.case` `.assessment` `.appointment` `.notification` `.report` `.knowledge` | 业务服务层 | Service 接口 |
| `counseling-api` | `.controller` `.config` `.security` | REST Controller、Spring Security | REST API（见 16 文档） |
| `counseling-app` | `.config` `.runner` | Spring Boot Main、配置装配、启动初始化 | — |

### 10.3 模块间交互方式

| 调用方 → 被调方 | 交互方式 | 说明 |
|------|------|------|
| Controller → Service | 同步方法调用 | 进程内 |
| Service → AI Orchestrator | 同步/异步（虚拟线程） | 对话走同步，摘要/报告走 `@Async` |
| Service → Domain Mapper | MyBatis-Plus 调用 | 自动租户拦截 |
| Advisor 链内 | Spring AI Advisor 链 | `getOrder()` 控制顺序 |
| 安全事件通知 | Spring ApplicationEvent | 进程内事件（风险触发→通知→审计） |

## 11. 关键配置示例

### 11.1 application.yml 核心配置

```yaml
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:5432/counseling
    username: ${DB_USER}
    password: ${DB_PASS}
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5

  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: 6379

  ai:
    openai:  # 供应商无关，可切换
      api-key: ${LLM_API_KEY}
      base-url: ${LLM_BASE_URL:https://api.openai.com}
      chat:
        options:
          model: ${LLM_MODEL:qwen-max}
          temperature: 0.3
          max-tokens: 500

# 租户配置
counseling:
  tenant:
    default-schema-prefix: tenant_
    fail-fast-on-missing: true  # 无租户上下文时快速失败

  # AI 安全配置
  ai:
    safety:
      max-turns-per-session: 12
      max-session-duration-minutes: 20
      max-sessions-per-day: 2
      crisis-hotline: "400-161-9995"
      output-guard-enabled: true

  # 数据保留策略
  retention:
    normal-session-days: 30
    high-risk-session-days: 365
    audit-log-years: 3
```

### 14.2 Advisor 链路线定稿（现状 vs 目标）

**定稿：Service 层显式安全管线为正式路线，非过渡态；Advisor 链降级为可选重构。**理由：①显式调用的安全顺序在代码中可读可测（安全合规 > 一致性），儿童安全场景不宜把硬短路埋进框架回调链；②世界B接线（13 §十三 TriageCall）后编排主体是状态机而非 Advisor 链，两套编排并存违背 KISS；③Spring AI Advisor API 仍在演进，重构收益不抵迁移风险。§4.2 保留作为目标态参考，不再作为待办。

**收敛后目标架构（不画第三套图，以 13 §十三为准）**：请求 → Service 安全前置（风险检测+脱敏）→ TriageCall（非流式分诊）→ CbtStateMachine 选择阶段 prompt → LLM 流式生成（SSE）→ 输出审查（RISK-201~204 独立化后可阻断/改写）→ 记忆/画像回注。
