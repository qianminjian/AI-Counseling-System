# 83 服务降级监控与告警设计（方案 + SPEC）

> 状态：doing（未冻结） | 创建：2026-08-09 | 更新：2026-08-09（方案核对代码定稿 + 补 SPEC 章节 + 与后台管理端衔接整合 OPS-MON-007/008） | 触发：BUG-TTS-01 事故复盘
> 事故：CosyVoice 主引擎因 dashscope SDK API 变更 100% 失败，系统静默降级 edge-tts 长期运行，**无任何告警触达管理员**。

## 一、设计目标

| # | 目标 | 度量 |
|---|------|------|
| G1 | 服务**运行期降级**可观测（主引擎失效但兜底可用） | 降级事件计数 > 0 即可见 |

## 三、方案设计

### 3.1 指标埋点（服务内，改动最小）

**TTS（tts-service）**：新增降级事件计数器，在策略层 `synthesize_with_degradation` 返回后打点：

```
tts_degraded_events_total{direction="cosyvoice->edge_tts"}   # Counter，策略降级时 +1
```

- 判定：`result.engine != 首选引擎(backends[0].name)` 且 `result.retried == false`（instruct 无指令重试成功不算降级，仍记 cosyvoice_fallback）
- **实现约束**：现有 `Metrics` 类为单 label key 结构（`_counters: label -> count`，渲染时固定 `label_key`），不支持双标签 → 新增独立 `_degraded_metrics = Metrics()` 实例，label 用 `direction` 拼接（`"cosyvoice->edge_tts"`），`/metrics` 端点追加一段 render（counter 名 `tts_degraded_events_total`、label_key `direction`；duration 传 0.0，不污染原 summary）
- 同时保留现有 `tts_synthesize_requests_total{engine}`（成功引擎分布）——降级率 = degraded / requests
- 埋点位置：app.py `synthesize()` 成功路径 `_metrics.record(engine_label, ...)` 旁（约 8 行改动）

**后端（counseling-ai）**：**已埋点，零改动**——`ResilientChatModel` 已有 `mindsafe.llm.model_fallback{from,to}` Counter（主模型异常 → 备用模型时 +1，Micrometer 导出为 `mindsafe_llm_model_fallback_total`）。本次仅补告警规则（§3.2），不新增指标（YAGNI：reason 维度可从 WARN 日志追查，不建多标签）。

**Voice（voice-service）**：已覆盖（`voice_asr_ready`/`voice_ser_ready`/`voice_analyze_requests_total{result}`），不新增。

### 3.2 告警规则（alert-rules.yml 新增 3 条）

```yaml
# 主引擎失效但兜底可用（本次事故场景：CosyVoice 100% 失败静默降级）
- alert: TtsPrimaryEngineDegraded
  expr: |
    sum(rate(tts_synthesize_requests_total{engine="edge_tts"}[5m])) > 0
    and sum(rate(tts_synthesize_requests_total{engine="cosyvoice"}[5m])) == 0
    and sum(rate(tts_synthesize_requests_total[5m])) > 0
  for: 5m
  labels: { severity: warning, team: platform }
  annotations:
    summary: "TTS 主引擎（CosyVoice）持续降级"
    description: "近 5 分钟全部合成走 edge_tts，CosyVoice 0 成功——检查 dashscope SDK 版本/API Key/配额。"

# 降级率超过 30%
- alert: TtsDegradeRatioHigh
  expr: |
    sum(rate(tts_degraded_events_total[5m]))
      / clamp_min(sum(rate(tts_synthesize_requests_total[5m])), 0.001) > 0.3
  for: 10m
  labels: { severity: warning, team: platform }
  annotations:
    summary: "TTS 降级率过高"
    description: "主引擎降级率 {{ $value | humanizePercentage }} 持续 10 分钟。"

# LLM 主备切换（服务可用但主供应商异常；复用 ResilientChatModel 现有计数器）
- alert: LlmPrimaryFailing
  expr: sum(rate(mindsafe_llm_model_fallback_total[10m])) > 0
  for: 5m
  labels: { severity: warning, team: platform }
  annotations:
    summary: "LLM 主供应商连续失败"
    description: "近 10 分钟发生 {{ $value }} 次主→备切换，检查主 Key 余额/限流/服务状态。"
```

**规则设计要点**：
- 主引擎降级规则用**成功计数**推导（cosyvoice 0 成功 + edge_tts > 0），不依赖新指标也能成立（兼容未埋点期）
- 降级率规则用新指标，阈值 30% 防抖动；`for: 10m` 避免瞬时毛刺
- 全部 warning 级（服务仍可用），critical 留给全引擎不可用（已有）

### 3.5 降级事件检测与落库（degradation_events，衔接管理端 M3 3.3）

自动降级事件由**监控侧检测器**落库（手动切换事件由管理端 API 直接写库，见管理端文档 §7.3）：

| 项 | 设计 |
|----|------|
| 数据源 | Prometheus 指标变化：`tts_degraded_events_total`（TTS 降级）、`mindsafe_llm_model_fallback_total`（LLM 切换）；ASR/SER 待规则扩展后接入（§七 后续） |
| 检测方式 | 后端定时轮询（30s，与 service_health_snapshots 采样同频）比对指标增量：增量 > 0 → 写一条 auto 事件；按 last_value 去重，连续轮询不重复写 |
| 恢复事件 | 主引擎成功计数恢复 / 降级率回落（如 TtsDegradeRatioHigh 恢复）→ 写 to_state=恢复档位事件（trigger_type=auto） |
| 落库 | `degradation_events` 表（结构见管理端文档 §6.5）：point/from_state/to_state/trigger_type=auto/operator=null/occurred_at |
| 与手动切换的关系 | 手动切换事件 trigger_type=manual（管理端写）；检测器**跳过已 manual 覆盖的点**（Redis 覆盖键存在时不写 auto 事件，避免双写） |
| 幂等 | 检测器多实例用 Redis SETNX 分布式锁（与逾期扫描任务同机制，管理端文档 R-9）；同 point 连续降级不重复写，恢复→再降级为新事件 |
| 组件落点 | `com.mindsafe.service.monitoring.DegradationEventDetector`（counseling-service，与 RiskNotifyRetryJob 同层——Mapper 依赖须在 service 层，分层纪律 T4）；`@Scheduled(cron 可配)`（项目已有先例：RiskNotifyRetryJob/DataRetentionCleanupJob/SlaEscalationScanner）；Mapper 复用 degradation_events（MyBatis-Plus）；Prometheus 查询用 RestTemplate（自建带超时，WeComAlertService 同模式） |

### 3.6 告警事件采集落库（alert_events，衔接管理端 M2 2.3）

M2 告警事件中心的历史查询依赖 `alert_events` 表（AlertManager 仅保留 120h），采集器归口本文档：

| 项 | 设计 |
|----|------|
| 数据源 | AlertManager API（`/api/v2/alerts`，容器内网可达，后端代理）+ 后端 AlertService 业务告警（WeComAlertService 已接线） |
| 采集方式 | 后端定时拉取（60s）AlertManager active/resolved 告警 → upsert `alert_events`（source=alertmanager）；AlertService 发出时同步写（source=alertservice） |
| 状态流转 | firing→resolved 更新 resolved_at；ack/closed 由管理端 API 更新（管理端文档 §7.2 POST /api/v1/ops/alerts/{id}/ack） |
| 落库 | `alert_events` 表（结构见管理端文档 §6.4） |
| 保留策略 | 保留 30 天，超期定时清理（与快照一致） |
| 组件落点 | `com.mindsafe.service.monitoring.AlertEventCollector`（counseling-service，同检测器）；`@Scheduled(cron 可配)`；AlertManager 访问走 RestTemplate（内网容器地址，管理端文档 §5.2 关键决策）；业务告警落库由 WeCom/LoggingAlertService sendAlert 尾部调用（可选注入，发出即留痕） |

## 八、to-spec 开发规格书（2026-08-09，对本文档 §一~§七 的规格化提炼）

> 说明：本规格书为开发启动的单一入口（等价发布至 issue tracker 的 ready-for-agent spec；本项目无外部 tracker，事实源即本文档，OPS-MON-001~008 已登记 TASK-TRACKER §三十）。

### 8.1 Problem Statement（问题陈述）

2026-08-09 生产事故（BUG-TTS-01）：CosyVoice 主引擎因 dashscope SDK API 变更 100% 失败，系统静默降级 edge-tts 长期运行，**无任何告警触达管理员**——管理员对"服务仍在运行但能力已降级"毫无感知。根因：① 监控栈（prometheus/alertmanager）配置存在但生产未部署；② 现有 `tts_engine_available` 指标只反映配置层可用性（SDK 已装 + key 非空 = 1），检测不到运行期降级（每次合成实际失败）。同类风险存在于 LLM 主备切换（已有指标但无规则）。

### 8.2 Solution（解决方案）

构建**服务降级监控链路**：运行期降级指标埋点（TTS 新增、LLM 复用）→ 告警规则（+3 条）→ 企微触达（≤5 分钟）→ 事件落库（降级事件/告警事件，供管理端消费）→ 生产部署 + 可重复演练验证。链路与后台管理端（AdminConsole）为数据-视图衔接关系：本链路产出数据，管理端 M2 告警中心/指标看板、M3 降级矩阵消费展示。

### 8.3 User Stories（用户故事）

1. As 平台管理员，I want TTS 主引擎（CosyVoice）失效但兜底引擎可用时降级事件可观测，so that 及时感知能力降级而非事后发现。
2. As 平台管理员，I want 降级持续 5 分钟时收到企微应用消息告警，so that ≤5 分钟内响应处置。
3. As 平台管理员，I want TTS 降级率超 30% 持续 10 分钟时收到告警，so that 识别趋势性劣化而非仅瞬时抖动。
4. As 平台管理员，I want LLM 主供应商连续失败（主→备切换）时收到告警，so that 检查主 Key 余额/限流/服务状态。
5. As 运维，I want 自动降级发生/恢复时事件自动落库（trigger_type=auto），so that 降级生命周期可追溯。
6. As 运维，I want 管理端手动切换事件同样落库（trigger_type=manual），so that 自动与人为干预在同一时间线可区分。

### 8.4 Implementation Decisions（实现决策）

- **指标契约**：新增 `tts_degraded_events_total{direction="cosyvoice->edge_tts"}`（Counter，策略降级时 +1）；复用 `mindsafe_llm_model_fallback_total{from,to}`（已存在，零改动）。判定：`result.engine != 首选引擎` 且 `非 retried`；instruct 无指令重试成功不计数；全失败 503 不计数。
- **埋点实现约束**：现 Metrics 为单 label key 结构（不支持双标签）→ 新增独立 Metrics 实例，label 用 direction 拼接，/metrics 追加独立 render 段（duration 传 0.0 不污染原 summary）。
- **告警规则契约（alert-rules.yml +3，全 warning 级）**：① TtsPrimaryEngineDegraded——成功计数推导（cosyvoice 0 成功 and edge_tts > 0 and 总请求 > 0，for 5m），不依赖新指标（兼容未埋点期）；② TtsDegradeRatioHigh——降级率 > 30%，for 10m 防毛刺；③ LlmPrimaryFailing——`rate(mindsafe_llm_model_fallback_total[10m]) > 0`，for 5m。critical 级留给全引擎不可用（既有规则）。
- **通知链契约**：企微应用消息（主，alertmanager wechat_configs 注入 WECOM_CORP_ID/AGENT_ID/SECRET/ALERT_TO_USER）+ 业务告警 webhook（辅，群机器人）+ 日志留存（兜底，缺配置时）；GRAFANA_PASSWORD 用 `:?` fail-fast 强制。
- **部署契约**：monitoring 栈三容器（prom 2.53.1/alertmanager 0.27.0/grafana 11.2.2），3 抓取端点（backend:8080/tts-service:10096/voice-service:10095），Grafana 仅 127.0.0.1:3002 可达（不公网暴露）。
- **降级事件检测器契约（OPS-MON-007）**：@Scheduled 30s 轮询（项目已有 @Scheduled 先例）；比对指标增量，增量 > 0 写 auto 事件；last_value 去重防连续重复；主引擎恢复/降级率回落写恢复事件；Redis 覆盖键存在时跳过该 point（避免与 manual 双写）；Redis SETNX 分布式锁防多实例重复；落库 `degradation_events`（point/from_state/to_state/trigger_type=auto/occurred_at）。
- **告警采集器契约（OPS-MON-008）**：@Scheduled 60s 拉取 AlertManager `/api/v2/alerts`（内网可达，后端代理）→ upsert `alert_events`（source=alertmanager）；AlertService 发出时同步写（source=alertservice）；firing→resolved 更新 resolved_at；ack/closed 由管理端 API 更新（管理端文档 §7.2）；保留 30 天定时清理。
- **组件落点**：DegradationEventDetector / AlertEventCollector 位于 counseling-api ops 监控包（与 M2/M3 API 同模块，MyBatis-Plus Mapper 落库）。
- **衔接契约**：OPS-MON-002/003/004/008 为管理端 M2（P1）数据前置；OPS-MON-007 为 M3（P2）数据前置；manual 事件与手动切换 API 在管理端文档设计实现。
- **执行顺序（依赖链）**：002（埋点）→ 003（规则）→ 004（部署）→ 005（演练）→ 007（检测器）→ 008（采集器）→ 006（归档）。

### 8.5 Testing Decisions（测试决策）

- **好测试的标准**：只断言外部行为（指标值 / 告警触达 / 落库记录），不测内部实现细节；每个 AC 对应可重复断言。
- **主 seam（唯一跨组件集成验证，最高 seam）**：端到端降级演练（AC-6）——断 DASHSCOPE key（或首选引擎不可用）→ 触发 1 次合成 → 断言指标 +1 → **≤5 分钟**企微应用消息收到 TtsPrimaryEngineDegraded → 恢复后指标停止增长。此为整个链路的验收门禁。
- **单元 seam（组件内）**：① tts-service 埋点单测（test_app.py 先例：正常路径不计数/503 不计数/instruct 重试成功不计数/降级 +1）；② counseling-api 检测器与采集器单测（mock Prometheus 查询响应与 AlertManager API；项目先例：RiskNotifyRetryJob / SlaEscalationScanner / DataRetentionCleanupJob 的定时任务测试模式）。
- **契约 seam（静态可测）**：`promtool check rules` 语法门禁（AC-4）+ curl 解析 /metrics 输出（AC-2）；规则表达式与计数器名一致性断言（AC-5）。
- **验收门禁**：AC-1~10 逐条对应（埋点/兼容/单测/规则语法/规则表达式/演练/部署/回归/检测落库/告警落库），006 归档前置为 AC-6 演练通过。
