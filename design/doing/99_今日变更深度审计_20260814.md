## 二、候选深化项（8 项）

### 白天 · BFS 遍历工具链

#### 候选 1【Strong】BFS 遍历引擎的「进程级全量重放」模型
- **Files**：`tools/browser-bfs/public-surface-bfs.mjs`（188 行）+ 白天 16:48-17:12 连续 7 个 fix(browser) 提交（实证）
- **问题**：`resetAndReplay()` 每次探索一个控件前从 URL 重新打开 + 逐步重放整条操作路径——重置成本 = O(路径深度) 次 CLI 调用，且每次都是新 spawnSync 进程（500 步 × 深度 4 ≈ 2000+ 次子进程启动）。白天 7 连修（avoid hanging page wait / bound command lifetime / terminate timed out commands / avoid duplicate navigation / isolate session cleanup / normalize control matching / record timeout）全部是此模型的次生灾害：进程级隔离把遍历状态压进 CLI 文本协议，任何挂起都变成 gtimeout 杀进程 + 状态不确定。
- **方案**：浏览器会话生命周期与遍历算法剥离——常驻会话 + 状态快照内存化 + **增量回退**（从最近快照回退 1 步，而非从 URL 全量重放）；遍历引擎与 CLI 适配层分文件。
- **收益**：局部性（状态管理与 BFS 队列同模块，CLI 为单一 seam）；杠杆（遍历成本 O(步数×深度)→O(步数)）；测试（引擎可注入假 CLI 纯测 BFS 逻辑——当前 7 连修全靠真机试错）。删除测试：删重放模型 → 状态漂移无法恢复，复杂度转移真机重跑。

#### 候选 2【Worth exploring】BFS cli() 脆弱接口面（JSON 混拼 + gtimeout 平台依赖）
- **Files**：`public-surface-bfs.mjs` cli/parseJson/snapshot/locatorAction（单文件 6 职责）
- **问题**：`parseJson` 从 stdout+stderr 混拼串「找第一个 {」解析 JSON——日志噪音先于 JSON 即解析失败；`gtimeout` 为 macOS 非内置命令（需 coreutils），CI/Linux 不可运行；`maxBuffer 4MB` 静默截断。单文件 6 个薄职责 = 浅模块。
- **方案**：CLI 适配层拆独立模块；JSON 输出专用通道（--json-only/输出文件），日志与数据分离；超时改 Node 原生 `AbortSignal.timeout()`。
- **收益**：接口面收窄为「进参数、出 JSON」单一契约；平台可移植；控件筛选/状态哈希保留纯函数可单测。

#### 候选 3【Speculative】EmotionSelect 删除唤醒模型预加载 — 与 BEACON 决策 #25 冲突
- **Files**：`frontend/student-h5/src/components/EmotionSelect.tsx` · BEACON 设计决策 #25
- **问题**：白天会话删除 `preloadWakeModel()`（情绪页预加载）且未同步任何设计文档——BEACON #25 明确「情绪选择页/登录页预加载（利用 TTS 播放时间窗口提前下载 whisper 模型）」。违反 core-red-lines §4.5 设计-代码一致底线。
- **方案**：确认删除动因（性能取舍 vs 误删）→ 回写 BEACON #25 附注（决策修订）或恢复代码。属治理动作非代码重构。

#### 候选 4【Speculative】useSseStream 超时命名误导（IDLE 实为连接建立超时）
- **Files**：`frontend/student-h5/src/hooks/useSseStream.ts`
- **问题**：`STREAM_IDLE_TIMEOUT_MS` 请求发起时启动、res.ok 后清除——语义是连接建立超时，命名暗示流空闲；超时直接 abort 无重试（LLM 首包延迟可能误杀正常对话）。
- **方案**：改名 `CONNECT_TIMEOUT_MS` 或接入 authFetch 重试语义；确需流空闲场景另设 reader 层超时。低风险小改。

### 晚上 · 安全/加密域（B-04/B-05/DB-ROLLBACK-01）

#### 候选 5【Strong】设备安全模块双装配缝（构造器歧义）
- **Files**：`backend/.../device/DeviceSecurityService.java`（205 行）· 今日 CI 实证（30 errors）
- **问题**：public 单参（测试用）+ public 双参（Spring 注入）双构造器无 @Autowired → Spring 无法决定注入点 → 全部 IT ApplicationContext 加载失败。测试缝与生产装配缝混在同一 public 接口面；任何双构造器 @Service 都会重复踩坑。
- **方案**：对齐 AliyunSmsService 先例——唯一 public Spring 构造器（@Value 注入）+ 包私有测试构造器；可固化为 check-commit 纪律钩子（检测 public 多构造器 @Service）。
- **收益**：装配决策收敛单点；模式固化后全仓库不再依赖 CI 试错。

#### 候选 6【Worth exploring】设备上报端点签名样板三重复
- **Files**：`DeviceController.java`（249 行）· `enforceRequestSignature`
- **问题**：heartbeat/reportStatus/reportVoiceprint 三端点各复制 3 个签名 header 参数 + 序列化 + 校验调用（5 行样板）；设备上报域是持续扩展面。
- **方案**：`HandlerMethodArgumentResolver` + `@DeviceSignature` 注解声明式横切。杠杆：新端点零样板；校验单点。风险：resolver 框架魔法需先例文档。

#### 候选 7【Worth exploring】加密字段清单散落三处（回填注册表面缺失）
- **Files**：`EncryptionBackfillService.java`（196 行，4 个 @FunctionalInterface）· FieldEncryptionService javadoc · V32/V49 迁移注释
- **问题**：「哪些字段被加密」散落三处，4 个函数式接口抽象面≈实现面；B-05 盘点四字段清单靠从代码反推（反向验证清单应是一等模块）。
- **方案**：`EncryptedFieldRegistry` 声明式注册表（实体类+方法引用保类型安全），回填/迁移注释/审计派生统一；测试收敛为 1 驱动用例 + N 字段断言。

#### 候选 8【Speculative】加密服务恒等透传 seam（enabled=false 语义隐形）
- **Files**：`FieldEncryptionService.java` · 8 个消费点
- **问题**：enabled=false 时 encrypt 恒等——调用方无法感知加密状态（B-05 靠反推代码才发现明文落库）。
- **方案与保留**：暴露 `isEnabled()` 接口成员；但删除测试显示恒等透传是「配置驱动的接口契约」而非浅抽象，Ciphertext 类型化改动面过大；收益有限，保持观察。
