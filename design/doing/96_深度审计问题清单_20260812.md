## 三、问题清单（按级别排序，均以 main 实态为准）

### 🔴 P0（生产阻断）——1 项

**P0-1｜dbbackups 备份卷无任何创建方，全新部署后每日备份必然静默失败**
- 位置：deploy/docker-compose.prod.yml（volumes 仅 pgdata/redisdata）、deploy/backup-common.sh:22-28
- 证据（亲验）：全仓 `grep -rn "dbbackups"` 仅 backup/restore/backup-common 引用，**无任何 compose 卷声明、无 `docker volume create`**；backup-common.sh 探测 `*_dbbackups` 卷为空即 `exit 1`；cron `0 2 * * *` 已接线（setup-server.sh:110）但失败无告警。
- 影响：生产数据库**无有效备份** = 数据丢失风险。
- 修复（≤5 行）：compose 显式声明 `dbbackups` 卷（external: true + 文档化创建命令），或 backup-common.sh 探测空时**幂等自愈**创建 + 落日志。

### 🟠 P1（严重）——2 项

**P1-1｜生产宿主 nginx 无限流，AUD-030 安全门禁实际未生效**
- 位置：deploy/nginx/host/nginx.conf（902 行，`limit_req` 命中 **0** 处 vs default.conf 4 处，亲验）
- 证据：生产实际承载 80/443 的是宿主 nginx（DA-13），其文件无任何 `limit_req_zone`；AUD-030 限流只存在于 test/dev 用 default.conf。**历轮审计"✅ 一致"只验证了非生产文件——核查方法缺陷 + 台账失实**。
- 修复：host/nginx.conf 增加 `limit_req_zone` + /mindsafe/ 敏感前缀限流；verify-nginx 测试补 limit_req 存在性断言。

**P1-2｜模型缓存路径三处不一致 + SER 静默降级，生产情感识别可能长期失效**
- 位置：deploy/.env.example:111（`./cache/modelscope`）、deploy/scripts/prepare-funasr.sh:28（`/guju/mindsafe/cache`）、backend/voice-service/ser_engines.py:76-78（异常静默降级返回 None）
- 证据（亲验）：compose 挂载 `${MODEL_CACHE_DIR:-./cache/modelscope}` 而 prepare-funasr 默认下载到 `/guju/mindsafe/cache`，`FUNASR_CACHE_DIR` 全仓 0 消费者；模型缺失时 SER 静默降级，对应告警仅 warning 级（alert-rules.yml:115-123）——**生产情感识别可能长期失效且无人知晓**。
- 修复：单一目录常量化（建议统一 `/guju/mindsafe/cache`），prepare-funasr/compose 挂载/.env.example 三处对齐；SER 模型缺失改启动 fail-fast 或升级告警级别。

## 五、过度设计质疑清单

> ⚠️ 2026-08-12 复核修正（用户质疑后逐项亲验代码）：1/2 项基于对 main 代码的不准确理解（疑似 dev 分支误读），
> 合并建议撤销；3 项方向成立，排期实施。详见 §十三。

1. **Prompt 领域四服务并存**（PromptTemplateService / PromptAssemblyService / PromptVersionService / PromptOrchestrationService）：TemplateService 与 AssemblyService 的 render 能力重叠 → 合并 TemplateService 入 AssemblyService，保留版本路由与编排两服务
   - **【复核结论】❌ 撤销合并**：render（classpath 资源加载+{{var}} 替换）与 assemble（版本路由+段落拼接）职责不同且跨模块；真问题 = AssemblyService 模板 key 字面量（"EMO_001"/"TSK_004"/"SYS_001"）未引用 TemplateService 常量 → 常量收编（F-05）
2. **情绪三组件**（EmotionStateMachine / EntryMoodStrategyResolver / ReplyEmotionResolver）：resolveWithTransition 同时承担状态机转移 + 策略解析，边界模糊 → 状态机与入场策略合并为单一情绪编排组件
   - **【复核结论】❌ 撤销合并**：resolveWithTransition 位于 PromptOrchestrationService（编排器 Facade 模式），状态机/策略解析/回复表达三组件输入输出方向各异，边界清晰；mapVoiceEmotion 为转发非双份实现 → 无需动作（F-06 关闭）
3. **CrisisResourceProvider vs CrisisHotlineProvider**：仅多一个 getHotlineNumber() 转发 → 折叠为单 Provider（B1 五源收敛已达成，额外一层无收益）
   - **【复核结论】✅ 方向成立**：ResourceProvider 无独立状态（3 个话术组装方法 + 1 转发），可并入 CrisisHotlineProvider；6 调用点 + 测试迁移（F-04，dev 分支已有等价收敛先例）
4. **dm_audit + dm_metrics（~670 行 bash + R1-R6 回归 + p90 基线 + 失败模式知识库）**：有事故背景（BUG-TTS-01 复盘）与完整测试支撑，可辩护但偏重；对单人运维团队维护成本/收益比存疑 → P3 关注，不强制拆
5. **TTS 7×8×10 名义矩阵**：emotion_capable 仅 1、dialect_capable 仅 1（OD-010 已裁决"矩阵 90% 死配置"）——名义能力密度显著高于实际可表达组合

**已复核不质疑项**：覆盖键（RUNTIME-001/002 fail-open）、SER_ENABLED 解耦 gauge（DA-02）、nudge Lua 原子化——设计合理。
