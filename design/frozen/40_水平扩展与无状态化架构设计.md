# 40 - 水平扩展与无状态化架构设计

> 创建：2026-07-28 | 状态：设计完成，待实施 | 对应规划任务：PERF-005（design/30 §方向八）
>
> 定位：把当前"模块化单体 + 单实例"演进为**可水平扩展的无状态服务集群**，使同一后端镜像能在负载均衡后启动 N 个副本、任意实例可处理任意请求、任意实例宕机不丢用户会话。这是"单校 → 多校规模化"的承载底座，触发时机为规模化（P3，多校并发压力出现时启动）。

---

## 一、业界对标（避免空想的依据）

### 1.1 十二要素应用（The Twelve-Factor App）

Heroku 提出、业界公认的云原生应用基线。与水平扩展直接相关的三条：

| 要素 | 原则 | 本系统当前差距 |
|------|------|--------------|
| VI. 进程（Processes） | 应用是**无状态**进程，任何需持久化的数据写入后端存储（DB/Redis），**绝不依赖进程内存或本地磁盘** | ❌ 会话状态存于进程内 `ConcurrentHashMap` |
| VIII. 并发（Concurrency） | 通过**进程模型水平扩展**（多进程/多实例），而非单进程内加线程 | ❌ 当前单实例，靠 JVM 内并发 |
| IX. 易处理（Disposability） | 进程可**快速启动、优雅关闭**，宕机不影响系统一致性（配合 crash-only 设计） | ⚠️ 优雅关闭已配，但内存态会随进程消失而丢失 |

**结论**：无状态化的核心动作 = **把一切"活在进程内存里的可变状态"外置到 Redis**，让实例本身变成"无记忆的计算单元"。

### 1.2 有状态长连接的两种扩展范式

对 SSE / WebSocket 这类长连接，业界有两条成熟路线：

| 范式 | 机制 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **粘性会话（Sticky Session）** | LB 按 client hash/cookie 把同一用户永远路由到同一实例，连接状态留在该实例本地 | 改造小，无需广播 | 实例宕机连接全断；负载不均；扩缩容需 rebalance | 连接状态强绑定单实例、无跨实例通信需求 |
| **无状态 + 消息总线广播** | 连接可落任意实例；需要跨实例送达的消息经 **Redis Pub/Sub**（或 MQ）广播，每个实例只推送落在自己身上的本地连接 | 实例对等、可任意扩缩容、宕机影响面小 | 需引入广播层、消息幂等 | 需要"一条事件送达所有相关在线用户"（本系统预警广播场景） |

**选型结论**：
- **SSE 对话流**：一次请求-一次流式响应，无跨实例送达需求 → **无需粘性、无需广播**，天然无状态（当前已用 Flux 实现，见 §2.1）。
- **WebSocket 预警推送**：一条预警需送达"该租户所有在线教师"，连接分散在多实例 → 采用**无状态 + Redis Pub/Sub 广播**范式。

> 参考实现：Spring Data Redis `RedisMessageListenerContainer` + `ReactiveRedisTemplate`/`RedisTemplate` 的 Pub/Sub；Spring Session 官方的 WebSocket 集群方案亦采用同一思路（发布者广播、各节点推本地 session）。

### 1.3 Redis 作为无状态化的共享后端

Redis 在本系统已作为限流后端就绪（§2.1）。业界将其用于三类会话外置：
1. **共享会话状态**（session state）——替代进程内 Map，key 带 TTL 自动回收
2. **共享缓存**（distributed cache）——Prompt/配置等热点数据多实例一致
3. **消息总线**（Pub/Sub）——跨实例事件广播

本设计三者都用到，避免为消息总线单独引入 Kafka/RabbitMQ（YAGNI：当前广播量小，Pub/Sub 足够；量级上来再评估 MQ）。

## 二、现状与差距（基于代码基线审计）

> 本节结论来自对 `counseling-api` / `counseling-service` / `counseling-ai` / `deploy` 的实际代码审计，逐项标注就绪度。

### 2.1 已就绪水平扩展的部分（✅ 无需改造）

| 能力 | 现状实现 | 为何已就绪 |
|------|---------|-----------|
| 认证鉴权 | `SecurityConfig` 设 `SessionCreationPolicy.STATELESS`，JWT 双 Token（access 2h / refresh 7d） | 无服务端 HttpSession，任意实例可独立验签 |
| 限流 | `RateLimiter` 用 `redisTemplate.opsForValue().increment(key)`，前缀 `ratelimit:`，30 次/分 | 计数已在 Redis，多实例共享额度 |
| SSE 对话流 | 用 Spring WebFlux `Flux<T>` 流式返回，**无进程内连接 Map** | 请求-响应式流，不跨实例，无共享状态 |

**关键判断**：鉴权、限流、SSE 三大高频路径已满足无状态要求，改造工作量集中在下述三处内存态。

### 2.2 需改造的进程内状态（❌ 阻碍水平扩展）

| 位置 | 现状 | 问题 | 目标 |
|------|------|------|------|
| `AlertWebSocketHandler` | `Map<UUID, Set<WebSocketSession>> tenantSessions = new ConcurrentHashMap<>()`；`pushAlert()` 只遍历**本进程**的 session | 多实例下，教师连到实例 A，预警在实例 B 触发 → 教师收不到 | Redis Pub/Sub 广播，每实例推本地连接 |
| `ConversationServiceImpl` | `Map<UUID, SessionState> activeSessions = new ConcurrentHashMap<>()`（含 emotionTag / turnCount / nudge 状态 / 情绪历史） | 用户下一轮请求落到另一实例 → 会话状态丢失、情绪历史断裂 | 迁移到 `ConversationStateManager`（Redis） |
| `PromptVersionService` / `PromptTemplateService` | 进程内 `Map<String, CachedPrompt> cache`（TTL 5min） | 各实例缓存副本不一致；A/B 分组、Prompt 版本更新在实例间存在窗口不一致 | 迁移至 Redis 共享缓存 |

### 2.3 已存在但未接线的关键资产（⭐ 复用优先）

| 资产 | 位置 | 状态 |
|------|------|------|
| `ConversationStateManager` | `counseling-ai/.../state/ConversationStateManager.java` | Redis 会话状态持久化**已实现**，key=`session:{sessionId}:state`，TTL 2h；Phase 1.6 规划但**未接线** |

> 这意味着会话状态外置的"存储层"已经写好，本设计的核心工作是**接线**（让 `ConversationServiceImpl` 读写它而非内存 Map），而非从零开发。这是"避免空想"的直接体现——设计建立在既有代码资产上。

### 2.4 负载均衡与部署现状

| 维度 | 现状 | 差距 |
|------|------|------|
| 后端实例数 | 单实例（`docker-compose.prod.yml` 中 `container_name: mindsafe-backend`，无 `replicas`） | 需支持多副本 |
| nginx 上游 | `proxy_pass http://backend:8080`（无 `upstream` 块） | 需 `upstream` 定义多后端 + 负载均衡策略 |
| SSE/WS 代理 | 已配 `proxy_buffering off`、WebSocket `Upgrade` 头 | ✅ 长连接代理已就绪 |

## 三、目标架构

### 3.1 架构总览

```
                    ┌─────────────────────────────┐
   Client ──────►   │  nginx (upstream + LB)      │
   (SSE/WS/HTTP)    │  least_conn + 健康检查        │
                    └───────┬─────────────┬───────┘
                            │             │
                   ┌────────▼──┐   ┌──────▼────┐   ... N 个对等无状态实例
                   │ backend-1 │   │ backend-2 │
                   └────┬──────┘   └─────┬─────┘
                        │                │
          ┌─────────────┼────────────────┼──────────────┐
          ▼             ▼                ▼              ▼
      ┌────────┐   ┌──────────┐   ┌────────────┐   ┌──────────┐
      │ Redis  │   │  Redis   │   │   Redis    │   │ Postgres │
      │会话状态 │   │ 共享缓存  │   │ Pub/Sub总线 │   │ (共享)    │
      └────────┘   └──────────┘   └────────────┘   └──────────┘
```

- N 个 backend 实例**完全对等、无本地状态**，可随时增减；单个 Redis/Postgres 仍是集中式（其自身高可用见 §六）。

### 3.2 WebSocket 预警广播的无状态化设计

改造 `AlertWebSocketHandler`，把"进程内直接推送"改为"经 Redis Pub/Sub 广播、各实例推本地连接"：

```
预警产生（实例 B）
   │
   ▼ PUBLISH 到频道 alert:tenant:{tenantId}  （载荷 = 预警 JSON）
Redis Pub/Sub
   │  订阅者 = 所有实例
   ├──────────────► 实例 A：收到消息 → 遍历本地 tenantSessions[tenantId] → 推送
   ├──────────────► 实例 B：收到消息 → 遍历本地 tenantSessions[tenantId] → 推送
   └──────────────► 实例 N：...
```

设计要点：
1. **本地 Map 仍保留**——每个实例维护自己的 `tenantSessions`（管理本机 WS 连接的生命周期），但**推送触发源**改为 Redis 订阅回调，而非直接方法调用。
2. **频道命名**：`alert:tenant:{tenantId}`，按租户隔离，避免跨租户消息扩散。
3. **发布入口**：预警服务不再直接调 `handler.pushAlert()`，改为 `PUBLISH`；`AlertWebSocketHandler` 启动时注册 `RedisMessageListenerContainer` 订阅该模式频道。
4. **幂等/去重**：预警载荷带 `alertId`；客户端按 `alertId` 去重（同一实例只推给自己本地连接，天然不会重复；跨实例不会重复推同一 session）。
5. **连接注册无需外置**：连接对象本身不可序列化，不入 Redis；只有"消息"经 Redis 流转。这与业界 Spring Session 集群 WebSocket 方案一致。

### 3.3 会话状态外置（接线 ConversationStateManager）

`ConversationServiceImpl` 移除进程内 `activeSessions`，改为通过 `ConversationStateManager` 读写：

| 项 | 设计 |
|----|------|
| 存储 key | `session:{sessionId}:state`（已定义） |
| 内容 | emotionTag、turnCount、nudge 冷场引导状态、情绪历史滑窗 |
| TTL | 2h（已定义），与 access token 生命周期同量级；每次交互刷新 TTL |
| 读写时机 | 每轮对话开始读、结束写（读-改-写） |
| 并发控制 | 同一会话串行（同一用户同一时刻单请求），无需分布式锁；若未来支持多端并发，用 `WATCH`/Lua 乐观更新 |
| 降级 | Redis 不可用时，退化为"本轮无历史上下文"（对话仍可进行，情绪历史丢失但不阻断），并告警 |

> 迁移策略：采用**双写过渡**——先让写路径同时写内存与 Redis、读路径优先 Redis，灰度验证一致性后再删除内存 Map，降低一次性切换风险。

### 3.4 Prompt 缓存共享化

`PromptVersionService` / `PromptTemplateService` 的进程内缓存改为 Redis：

| 项 | 设计 |
|----|------|
| key | `prompt:cache:{tenantId}:{templateKey}:{abGroup}` |
| TTL | 5min（沿用现值） |
| A/B 分组一致性 | `assignAbGroup` 的分组逻辑（`hashCode % 10 < 2` 为 treatment_a）是**纯函数**，多实例结果一致，无需外置；仅缓存内容外置 |
| 失效 | Prompt 版本发布时主动 `DEL` 对应 key，实现多实例秒级一致（当前进程内缓存做不到） |
| 降级 | Redis miss 时回源 DB（现有逻辑），不阻断 |

### 3.5 负载均衡（nginx upstream）

nginx 由单点 `proxy_pass` 改为 `upstream` 池：

| 项 | 设计 |
|----|------|
| 策略 | `least_conn`（最少连接优先）——SSE/WS 长连接场景比 round-robin 更均衡 |
| 健康检查 | 被动健康检查（`max_fails` + `fail_timeout`）；主动检查需 nginx-plus，社区版用 `/actuator/health` 配合被动探测 |
| 长连接 | 保持已有 `proxy_buffering off`（SSE）与 `Upgrade` 头（WS）配置到 upstream |
| 会话保持 | **不需要** sticky——因为状态已全部外置；任意实例可服务任意请求 |
| 扩缩容 | 增减 backend 副本后 reload nginx upstream 列表（或用 DNS/服务发现，见 §六演进） |

## 四、实施路径（分阶段，低风险优先）

| 阶段 | 内容 | 依赖 | 风险 |
|------|------|------|------|
| P5-1 | Prompt 缓存迁 Redis（改造面小、无长连接） | Redis（已就绪） | 低 |
| P5-2 | 会话状态接线 `ConversationStateManager`（双写灰度 → 切换） | Redis | 中（对话核心路径） |
| P5-3 | WebSocket 预警 Redis Pub/Sub 广播 | Redis Pub/Sub | 中（预警送达正确性） |
| P5-4 | nginx upstream + 后端多副本（compose `--scale` 或 replicas） | P5-1~3 全部完成 | 中（部署编排） |
| P5-5 | 多实例压测验证（500 并发 SSE + 预警广播送达率） | 全部 | — |

> 顺序原则：**先把状态外置（P5-1~3），再开多实例（P5-4）**。反过来会在改造期就暴露一致性 bug。P5-4 与 design/42 部署架构升级联动。

## 五、EARS 验收标准

| # | EARS 描述 |
|---|-----------|
| AC-1 | While 后端以 N≥2 副本运行，when 用户连续多轮对话请求被 LB 分发到不同实例，the 系统 shall 保持会话情绪历史与轮次计数连续（无因换实例而丢失） |
| AC-2 | While 教师 WS 连接在实例 A，when 学生对话在实例 B 触发高危预警，the 系统 shall 在 2s 内经 Redis Pub/Sub 将预警送达该教师 |
| AC-3 | When 管理员在任一实例发布新 Prompt 版本，the 所有实例 shall 在 ≤5min（或主动失效后立即）使用新版本，无实例间长期不一致 |
| AC-4 | If 某个 backend 副本宕机，then 其上的 SSE/WS 连接断开后，客户端重连 shall 被 LB 路由到健康副本并恢复服务，会话状态不丢失 |
| AC-5 | If Redis 不可用，then 对话 shall 降级为无历史上下文继续可用（不整体阻断），并触发告警 |
| AC-6 | While 500 并发对话 + 预警广播，the 系统 shall 满足预警送达率 ≥99%、SSE 首 token P95 不因多实例劣化 |

## 六、后续演进（超出本期范围，YAGNI 边界）

| 方向 | 何时考虑 | 说明 |
|------|---------|------|
| Redis 高可用（Sentinel/Cluster） | Redis 成为单点风险时 | 当前单 Redis，规模化后需哨兵/集群，否则 Redis 宕机=全站会话丢失 |
| 消息总线升级 MQ（Kafka/RocketMQ） | 广播量大/需持久化重放/削峰 | Pub/Sub 不持久化，订阅者离线即丢消息；量级上来再换 |
| 服务发现（Consul/K8s Service） | 副本频繁弹性伸缩 | 替代 nginx 静态 upstream 列表 |
| 容器编排 K8s | 多校多环境、需自动弹性 | 从 docker compose 迁 K8s，HPA 自动扩缩容 |
| 数据库读写分离/分库 | DB 成为瓶颈 | 见 design/41、PERF-002 |
