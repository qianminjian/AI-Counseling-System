> 创建：2026-07-28 | 状态：设计完成，待实施 | 对应规划任务：PROD-008 / PARENT-WX-001~006（design/30 §方向五、design/26 §2.2）
>
> 定位：设计将**家长端从当前的 Vite + React H5 单页应用（SPA）迁移为微信小程序**的技术路径。采用 **Taro 跨端框架**（React 语法一次编写，编译到微信小程序 + H5），实现"一套代码、双端产物"，同时保留 H5 链接入口。触发时机为 **H5 端稳定运行后**（P3，远期），需企业主体完成微信认证。

## 〇、现状澄清（重要：修正 design/26 的不一致）

> **必须先澄清一处文档与代码的偏差，避免基于错误前提做设计（红线：design/*.md 为单一事实源，需与代码核对）。**

design/26 §2「分阶段规划」与 PARENT-WX-004、§7 构建命令处写有"Taro 4 编译为 H5 / `taro build --type h5` / `taro build --type weapp`"，暗示家长端**已是 Taro 工程**、小程序化只需"同一 Taro 工程重新编译"（估 2-3 人天）。

**但实际代码并非如此**：

| 维度 | design/26 部分表述 | 实际代码（`frontend/parent-h5/package.json` 等） |
|------|-------------------|------------------------------------------|
| 框架 | 部分处称 "Taro 4" | **Vite 6 + React 19 + react-router-dom 7 + Sass**（无任何 Taro 依赖） |
| 构建 | `taro build` | `vite build` |
| 工程结构 | — | `vite.config.js` / `main.jsx`（React Router）/ `app.scss`，标准 React SPA |

> 注：design/26 §3「技术选型」与 §5「工程结构」本身写的就是 Vite+React，与其 §2/§7 的 Taro 表述**自相矛盾**。真实基线以代码为准 = **Vite + React SPA，不是 Taro**。

**结论**：小程序化**不是“重新编译”，而是一次真实的框架迁移**（React-SPA → Taro）。design/26 “2-3 人天、同一工程重编译”的估计**过于乐观、已修正**。本文按真实基线设计。design/26 §2/§7 的 Taro 表述**已同步修正（v1.1，见 §七）**。

## 一、业界对标（避免空想的依据）

### 1.1 微信小程序的技术形态与选型

小程序不是浏览器网页——它运行在微信的**双线程模型**（逻辑层 JSCore + 渲染层 WebView 隔离），**没有 DOM/BOM**，不能直接用 `document`/`window`，路由、组件、样式（WXSS）均为微信专有体系。因此 React SPA **不能直接跑**，必须迁移。三条主流路径：

| 路径 | 方案 | 复用度 | 适用 |
|------|------|-------|------|
| **A. 原生小程序重写** | 用微信原生框架（WXML/WXSS/JS）重写 | 仅 API/逻辑可复用 | 只做小程序、不要 H5 |
| **B. Taro 跨端框架** | React 语法编写，编译到 weapp + H5 + 其他小程序 | 高（一套代码多端产物） | **既要小程序、又保留 H5（本系统场景）** |
| **C. uni-app** | Vue 语法为主，编译多端 | 高 | 团队 Vue 栈为主时 |

**选型结论：路径 B（Taro）**。理由：
1. 本系统三前端均为 **React 栈**，Taro 用 React 语法，团队认知一致（KISS）。
2. 一套代码同时产出**微信小程序 + H5**，满足"小程序 + 链接入口并存"，避免双份维护（DRY）。
3. Taro 生态成熟（京东开源，社区活跃），支持编译到微信/支付宝/抖音等多端，未来可扩展。

> uni-app（Vue）不选：与团队 React 栈不一致，引入第二套心智负担。

### 1.2 React SPA → Taro 迁移的关键差异与踩坑（社区实践）

迁移不是换构建工具，需处理框架级差异：

| 差异项 | React SPA（现状） | Taro / 小程序 | 迁移动作 |
|--------|------------------|--------------|---------|
| 元素 | `<div>/<span>/<button>` | `<View>/<Text>/<Button>`（Taro 组件） | 视图层元素全部替换 |
| 路由 | react-router-dom（前端路由） | 小程序页面路由（`app.config` 注册 + `Taro.navigateTo`） | 路由体系重写 |
| 网络 | `fetch` | `Taro.request`（小程序无 fetch） | API 层封装换底层 |
| 存储 | `localStorage` | `Taro.setStorageSync`（小程序无 localStorage） | Token 存储层改造 |
| 样式 | SCSS + 任意选择器 | WXSS：**不支持部分复杂选择器、无标签选择器级联到自定义组件内部** | 样式改造（见下） |
| 生命周期 | React 组件生命周期 | 小程序页面生命周期（onLoad/onShow）+ React Hooks | Taro 已桥接，注意 onShow 等小程序特有钩子 |
| 尺寸单位 | px/rem | 推荐 `rpx`（响应式像素，750 设计稿基准） | 样式单位调整 |

**样式踩坑（社区高频问题，直接借鉴规避）**：
- 小程序自定义组件样式隔离，**外部类选择器默认无法穿透组件内部**；标签选择器（如 `div span`）在小程序内行为受限。
- 规避做法：**采用 BEM 类命名 + 必要时用 `style` 内联覆盖**，避免依赖后代/标签选择器级联；组件样式尽量自包含。
- 全局样式与页面样式分层，避免依赖 H5 下的 CSS 级联假设。

### 1.3 微信小程序上线的合规前置（硬门槛）

| 前置 | 说明 |
|------|------|
| 企业主体认证 | 小程序需企业主体（个人主体不能做涉及用户数据/教育类目），需营业执照（PARENT-WX-001 依赖） |
| 类目审核 | 教育 / 工具类目，可能需相关资质证明 |
| 用户隐私保护指引 | 微信要求声明所收集信息（手机号等），配置隐私协议（对齐 design/22 告知同意） |
| 手机号获取 | `getPhoneNumber` 需企业认证 + 用户主动授权，不能静默获取 |
| 内容合规 | 涉及未成年人心理数据，审核趋严，需明确数据用途与最小必要 |

> 这些是提审门槛（PARENT-WX-005），须在开发前确认，避免做完被拒。属监管/主体事项（红线 §7），AI 只提示不代办。

## 二、现状与迁移复用分析（基于真实基线）

家长端功能极简（3 个页面，只读为主），迁移面可控。按真实的 Vite+React 基线分析复用度：

| 层 | 现状 | 迁移到 Taro 的复用度 | 迁移动作 |
|----|------|-------------------|---------|
| API 逻辑（端点契约） | `src/api/index.js` 用 `fetch` 调 4 个 `/parent/*` 端点 | 契约 100% 复用，**底层 `fetch` → `Taro.request`** | 重写请求封装，业务调用签名不变 |
| 业务逻辑/工具 | `src/utils/auth.js`（Token 管理，用 localStorage） | 逻辑复用，**`localStorage` → `Taro` 存储 API** | 存储层适配 |
| 视图层 | 3 页 `.jsx`（verify/report/consent），HTML 元素 + SCSS | 结构可参考，**元素/样式需按 Taro 组件与 WXSS 重写** | 视图层重写（工作量主体） |
| 路由 | react-router-dom（`/`、`/report`、`/consent`） | **重写为小程序页面路由** | 路由重写 |
| 认证流程 | H5：初始 Token（`?token=`）→ 手机验证码 → 7 天 Token | 小程序补 `wx.login`→openid→`parent_bindings` 绑定（或沿用手机验证码） | 认证流程增强（见 §3.3） |

> **真实工作量**：并非 design/26 的"2-3 人天重编译"。实际是"引入 Taro 工程 + 视图层重写 + 路由重写 + 存储/请求适配 + 微信认证接入 + 提审"，属**一次完整的小程序开发**，只是业务简单（3 页）故总量可控。

### 2.1 后端 API 复用（无需改动）

design/26 §6 的 4 个家长端端点已实现且为标准 REST，小程序沿用同一套 API（Bearer Token）：

| 端点 | 复用 |
|------|------|
| `POST /api/v1/parent/send-code` | ✅ 直接复用 |
| `POST /api/v1/parent/verify-phone` | ✅ 直接复用（小程序也走手机验证码路径） |
| `GET /api/v1/parent/report` | ✅ 直接复用 |
| `POST /api/v1/parent/consent/withdraw` | ✅ 直接复用 |

小程序新增的仅是**微信登录绑定**（`wx.login`→后端换 openid，写 `parent_bindings`）——需后端补一个绑定端点（design/26 提及 `parent_bindings` 表已设计）。

## 三、迁移设计

### 3.1 工程架构（Taro 一码多端）

```
frontend/parent-mini/            # 新 Taro 工程（或原地改造 parent-h5）
├── src/
│   ├── app.config.ts            # 小程序全局配置（页面注册/窗口/tabBar）
│   ├── app.tsx                  # 入口
│   ├── pages/
│   │   ├── verify/index.tsx     # 手机验证（+ 小程序 wx.login 绑定）
│   │   ├── report/index.tsx     # 情绪周报
│   │   └── consent/index.tsx    # 同意管理
│   ├── services/                # API 层：Taro.request 封装（契约同 design/26 §6）
│   └── utils/                   # Token 存储（Taro storage）
├── config/                      # Taro 编译配置（weapp / h5 分别产物）
└── project.config.json          # 微信开发者工具工程配置（AppID）
```

产物：`taro build --type weapp`（小程序） / `taro build --type h5`（保留 H5 链接入口）。

### 3.2 视图与样式迁移

| 项 | 设计 |
|----|------|
| 元素替换 | `div→View`、`span/文本→Text`、`button→Button`、`img→Image` |
| 样式 | SCSS → WXSS 兼容子集；采用 **BEM 命名**，避免标签/后代选择器穿透组件；尺寸用 `rpx`（750 基准），沿用移动端居中布局 |
| 图表 | 现有情绪分布用纯 CSS 条形（design/26 §4.3），小程序内继续用 `View` + 宽度百分比实现，避免引入不兼容的图表库 |
| 弹窗 | 撤回同意二次确认改用小程序 `Taro.showModal` |

### 3.3 认证流程（H5 与小程序双路径）

| 环境 | 流程 |
|------|------|
| H5（保留） | 链接 `?token=` → 手机验证码 → 7 天 Token（localStorage/Taro storage）——**与现状一致** |
| 小程序（新增） | ① `wx.login` 拿 code → ② 后端 code 换 openid → ③ 查 `parent_bindings`：已绑定则签发 Token；未绑定则走手机验证码 + `getPhoneNumber` 完成绑定 → ④ Token 存 Taro storage |

要点：
- 小程序手机号（`getPhoneNumber`）需企业认证 + 用户授权，**不可静默获取**。
- Token 与 H5 同构（复用后端 7 天 Token 机制），后端只需新增"openid 绑定/查询"端点。
- 手机号脱敏、只读原则、撤回不可逆等安全约束**完全沿用 design/26 §8**。

### 3.4 消息推送（PARENT-WX-006）

小程序周报通知用**微信订阅消息**（`requestSubscribeMessage`，用户一次授权、模板消息推送），替代 H5 无法主动推送的短板：
- 家长在小程序内主动授权订阅"周报更新"模板消息。
- 后端周报生成后经微信订阅消息 API 推送（需模板 ID、企业配置）。
- 属锦上添花，非首版必需（YAGNI，可 PARENT-WX-006 单列后置）。

## 五、EARS 验收标准

| # | EARS 描述 |
|---|-----------|
| AC-1 | The 家长端 shall 由同一 Taro 工程编译出微信小程序与 H5 两套产物，业务逻辑不重复维护 |
| AC-2 | When 家长在微信小程序内首次进入，the 系统 shall 通过 `wx.login`→openid 识别；已绑定直接签发 Token，未绑定引导手机验证码绑定 |
| AC-3 | While 运行于小程序，the 手机验证 / 周报查看 / 同意撤回三大功能 shall 与 H5 行为一致，复用同一套后端 `/parent/*` API |
| AC-4 | The 小程序 shall 仅在用户主动授权后获取手机号（`getPhoneNumber`），不静默获取 |
| AC-5 | The 小程序样式 shall 不依赖被小程序限制的选择器（标签/后代穿透），在真机上渲染与设计稿一致 |
| AC-6 | While H5 与小程序并存，the H5 链接入口 shall 持续可用，迁移不中断现有家长访问 |
| AC-7 | The 小程序上线前 shall 完成企业主体认证、类目审核、隐私协议配置（对齐 design/22），未完成不得提审 |
