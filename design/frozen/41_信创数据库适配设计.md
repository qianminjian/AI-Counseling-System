# 41 - 信创数据库适配设计

> 创建：2026-07-28 | 更新：2026-08-05 | 状态：设计完成，待实施 | 对应规划任务：BIZ-005 / DEC-006 / RISK-004（design/30 §方向七）
>
> **DEC-006 决策跟踪（2026-08-05 并入本专题）**：信创数据库选型（达梦 vs 人大金仓）属监管/采购决策，随本专题冻结跟踪（TASK-TRACKER §二 DEC-006 已置 🔒）。解冻触发：进入政企/教育局信创化采购要求（M3+）时，由钱敏健结合 DBAD-001 兼容性评估议决；AI 仅提供技术评估（41 §1.1 选型初步结论：人大金仓 PG 内核迁移成本最低）。
>
> 定位：评估并设计从 **PostgreSQL 16 + pgvector** 迁移到**国产信创数据库（达梦 DM8 / 人大金仓 KingbaseES）**的技术路径，识别兼容性风险点，给出适配方案与替代评估。触发时机为进入**政企/教育局采购信创化要求**的市场（M5+，P3），非当前商用必须项——当前 PG 完全满足，本文是"来了再动"的预案，避免过早适配增加负担（YAGNI）。

## 一、业界对标（避免空想的依据）

### 1.1 信创数据库的政策背景与选型格局

- **政策驱动**：党政、金融、教育等关键信息基础设施领域的国产化替代（信息技术应用创新，简称"信创"）要求数据库、中间件、操作系统使用国产自主可控产品。教育局级采购在部分省份已将信创作为准入项。
- **主流国产关系型数据库**（均宣称高度兼容 Oracle/PostgreSQL 生态）：

| 数据库 | 厂商 | 兼容底座 | 生态成熟度 | 与本系统关系 |
|--------|------|---------|-----------|-------------|
| **达梦 DM8** | 武汉达梦 | 兼容 Oracle 语法为主，亦支持 PG 迁移 | 党政金融广泛部署，工具链完善 | 候选一 |
| **人大金仓 KingbaseES** | 人大金仓 | **基于 PostgreSQL 内核**，PG 兼容性最好 | 电子政务市占高 | **候选一（PG 内核，迁移成本最低）** |
| GaussDB / openGauss | 华为 | 基于 PG 内核（openGauss 开源） | 金融运营商 | 备选 |
| TiDB / OceanBase | PingCAP / 蚂蚁 | MySQL 兼容为主 | 分布式，非本系统迁移首选 | 不优先 |

**选型初步结论**：本系统 ORM 层与 SQL 大量使用 PostgreSQL 特性，**人大金仓 KingbaseES（PG 内核）迁移成本最低**，应作为首选适配目标；达梦 DM8 作为并行候选（部分客户指定达梦）。最终选型属监管/采购决策（DEC-006），AI 只提供技术评估，不做决策（红线 §7）。

### 1.2 迁移工具链（业界成熟方案）

| 目标库 | 官方迁移工具 | 能力 |
|--------|------------|------|
| 人大金仓 | KDMS（KingbaseES Database Migration System） / KStudio | schema + 数据 + 对象迁移，PG 源兼容度高 |
| 达梦 | DTS（DM 数据迁移工具） | 支持从 PG/Oracle/MySQL 迁移表结构与数据 |

**方法论对标**：数据库迁移业界通用四步——**评估（兼容性扫描）→ schema 转换 → 数据迁移 → 应用适配与回归**。本文 §三～§五对应这四步。

## 二、现状与迁移风险点（基于代码基线审计）

> 本系统 ORM 为 **MyBatis-Plus 3.5.9**（非 JPA），SQL 分布在 Mapper XML 与注解中，PG 特有用法是迁移的主要风险。以下逐项审计。

### 2.1 兼容性风险清单（按风险等级）

| # | PG 特性 | 使用位置 | 风险 | 信创适配方案 |
|---|---------|---------|------|-------------|
| R1 | **pgvector 向量检索**（`<=>` 余弦距离、`vector` 类型） | RAG 心理知识库（design/15，AI-006）；`counseling-ai` VectorStore | 🔴 高——国产库向量能力参差 | 见 §四专项评估 |
| R2 | **JSONB 类型**（`JsonbTypeHandler` 用 `PGobject.setType("jsonb")`） | 多实体（画像、量表 license_info、配置等） | 🔴 高——`PGobject` 是 PG JDBC 专有类 | 见 §3.2 |
| R3 | **Schema 级多租户隔离**（`AbstractRoutingDataSource` 动态切 `tenant_{id}` schema） | design/07 多租户；`counseling-tenant` | 🟡 中——国产库 schema 语义差异 | 见 §3.3 |
| R4 | **ON CONFLICT ... DO UPDATE**（upsert） | 多处 Mapper | 🟡 中——语法方言差异 | 方言层改写 |
| R5 | **序列 / SERIAL / `nextval`** | 主键生成（部分表） | 🟢 低——国产库均支持，语法微调 | 方言层 |
| R6 | **类型转换 `::` 语法**（如 `'x'::jsonb`、`::timestamptz`） | SQL 片段 | 🟡 中——达梦不支持 `::`，需改 `CAST()` | 方言层改写 |
| R7 | **时间类型 `timestamptz` / `now()` / `interval`** | 时间字段与查询 | 🟢 低——语义兼容，函数名可能微调 | 方言层 |
| R8 | **分页/LIMIT OFFSET** | MyBatis-Plus 分页插件 | 🟢 低——MP 有对应方言 `Dialect` | 配置 MP 方言 |
| R9 | **pg_dump / psql 相关运维脚本** | `deploy/` 备份恢复、`pg-init.sql` | 🟡 中——迁移后备份工具链需替换 | 见 design/42 联动 |

### 2.2 MyBatis-Plus 方言支持现状

MyBatis-Plus 内置分页方言（`DbType`）包含 `DM`（达梦）、`KINGBASE`（人大金仓）、`POSTGRE_SQL` 等。**分页层（R8）改造成本低**——切换 `DbType` 即可。风险集中在 R1/R2/R3/R6 这些**非分页的 SQL 语义与专有类型**。

## 三、适配设计（关系型部分）

### 3.1 抽象隔离原则：收敛数据库方言到单一适配层

当前 PG 特有用法散落各处，直接迁移会遍地改。设计目标是**先收敛、后适配**：

| 层 | 改造 |
|----|------|
| TypeHandler 层 | JSONB 处理抽象为接口，PG/信创各一实现（§3.2） |
| 数据源路由层 | schema 隔离逻辑抽象，兼容国产库 schema 语义（§3.3） |
| SQL 方言 | ON CONFLICT / `::` / 函数名 由方言适配类统一改写；分页交给 MP 方言 |
| 配置 | 通过 `spring.profiles`（如 `db-pg` / `db-kingbase` / `db-dm`）切换驱动、方言、连接串 |

> 原则：**同一套业务代码 + 可插拔方言层**，而非维护两套代码库（DRY）。

### 3.2 JSONB 适配（R2，风险最高的类型问题）

现状 `JsonbTypeHandler` 直接依赖 PG 的 `org.postgresql.util.PGobject`：

| 目标 | 方案 |
|------|------|
| 人大金仓 | KingbaseES 有对应 JSONB 与 `KBobject`（PG 内核，行为接近），可提供 Kingbase 版 TypeHandler |
| 达梦 | DM8 无原生 JSONB，需评估：① 用 `TEXT/CLOB` 存 JSON 字符串 + 应用层序列化；② 用 DM 的 JSON 函数（若版本支持） | 
| 抽象 | 定义 `JsonTypeHandler` 抽象，按 profile 注入 PG/Kingbase/DM 实现；业务实体不感知底层类型 |

> ⚠️ 达梦若退化为 TEXT 存储，会**失去 JSONB 的索引与路径查询能力**（如 `->>`、GIN 索引）。需审计现有代码是否有基于 JSONB 的查询过滤——若仅存取整块 JSON（大概率），退化为 TEXT 影响可控；若有 JSONB 路径查询，需改为应用层过滤或宽表化。**此项须在迁移评估阶段实测确认。**

### 3.3 Schema 级多租户隔离适配（R3）

本系统用 `AbstractRoutingDataSource` 按租户动态切换到 `tenant_{id}` schema（design/07）：

| 目标库 | schema 语义 | 适配 |
|--------|-----------|------|
| 人大金仓 | PG 内核，支持 `search_path` / schema，行为接近 PG | 迁移成本低，验证 `set search_path` 或连接级 schema 切换有效 |
| 达梦 | 达梦"模式（SCHEMA）"概念存在但与用户强绑定，切换语义不同 | 需评估：连接级切 schema 是否可行；若不行，退化为"每租户独立用户/表前缀"方案 |

> 多租户隔离是 SaaS 核心（design/07），信创迁移**不得降低隔离强度**。达梦若 schema 切换语义不兼容，须设计等价隔离方案并做安全评审。

### 3.4 SQL 方言改写（R4/R6/R7）

| PG 写法 | 达梦适配 | 金仓适配 |
|---------|---------|---------|
| `INSERT ... ON CONFLICT DO UPDATE` | `MERGE INTO`（达梦支持）或存储过程 | 金仓 PG 内核多支持 ON CONFLICT，验证 |
| `'x'::jsonb`、`col::text` | 改 `CAST(x AS ...)` | 金仓多兼容 `::`，验证 |
| `now()`、`interval '1 day'` | DM 用 `SYSDATE` / `INTERVAL` 语法微调 | 金仓兼容 |

改写策略：**扫描全部 Mapper XML + SQL 注解**建立"PG 专有语法清单"，逐条给出目标方言等价写法，由方言适配层或迁移期人工改写覆盖，纳入回归测试。

## 四、向量检索能力专项评估（R1，最高不确定性）

RAG 心理知识库（design/15）依赖 pgvector 的 `vector` 类型与 `<=>` 余弦相似度检索。这是信创迁移**最不确定**的一环，单列专项。

### 4.1 国产库向量能力现状

| 库 | 向量支持 | 评估 |
|----|---------|------|
| 人大金仓 | 部分版本提供向量扩展/兼容 pgvector 的插件（需确认目标版本） | 若支持 pgvector 兼容接口，改造小 |
| 达梦 | DM8 较新版本宣称支持向量类型与检索 | 需实测检索精度与性能、语法差异 |
| 外置向量库 | 独立部署 Milvus / 国产向量数据库 | RAG 向量与业务库解耦，规避关系库向量能力不足 |

### 4.2 三条可选路径（按迁移成本排序）

| 路径 | 方案 | 适用 |
|------|------|------|
| **A. 目标库原生向量** | 用金仓/达梦自带向量能力，改 `<=>` 为其等价算子 | 目标库向量能力达标时首选，架构最简 |
| **B. 向量检索外置** | RAG 向量存独立向量库（Milvus 等），业务库只存关系数据；Spring AI VectorStore 换实现 | 目标库向量能力不足/性能差时；也利于向量与业务解耦 |
| **C. 降级检索** | 关键词/全文检索替代向量语义检索（临时） | 向量能力完全缺失且工期紧的兜底，效果下降 |

> **推荐**：优先验证路径 A（实测目标库向量检索的召回与性能）；若不达标转路径 B（外置向量库，架构上也更清晰）。路径 C 仅作兜底。此决策依赖实测数据，属评估阶段结论，本设计不预设。

## 五、迁移实施路径（评估→转换→迁移→回归）

| 阶段 | 内容 | 产出 |
|------|------|------|
| M-0 兼容性评估 | 用目标库迁移工具（KDMS/DTS）扫描；建立 R1~R9 逐项实测结论表 | 兼容性评估报告 + 阻塞项清单 |
| M-1 方言层建设 | 抽象 JsonTypeHandler、数据源路由、SQL 方言适配；引入 `db-*` profile | 可插拔方言层（PG 仍为默认） |
| M-2 Schema 转换 | 工具生成目标库 DDL；人工修正类型（JSONB/vector/序列） | 目标库建库脚本 |
| M-3 数据迁移 | 工具迁移存量数据；校验行数/校验和/抽样一致性 | 迁移+校验脚本 |
| M-4 向量方案落地 | 按 §四选定路径实施 RAG 向量迁移 | 向量检索回归通过 |
| M-5 应用回归 | 全量集成测试 + 多租户隔离验证 + 性能对比 | 回归报告，PG↔信创双跑对比 |
| M-6 运维适配 | 备份/恢复/监控工具链替换（联动 design/42） | 信创环境部署手册 |

> 全程保持 **PG 为默认、信创为可切换 profile**，不做"一刀切替换"，支持同一代码库服务 PG 客户与信创客户（多市场并存）。

## 六、EARS 验收标准

| # | EARS 描述 |
|---|-----------|
| AC-1 | When 以 `db-kingbase`（或 `db-dm`）profile 启动，the 系统 shall 完成建表、CRUD、多租户 schema 切换全部核心功能，无 PG 专有语法报错 |
| AC-2 | While 运行于信创库，when 执行 JSONB 字段读写，the 系统 shall 正确存取（金仓等价 JSONB；达梦按选定方案），业务语义不变 |
| AC-3 | While 运行于信创库，the 多租户数据隔离强度 shall 不低于 PG 环境（跨租户不可越权访问） |
| AC-4 | When 执行 RAG 语义检索，the 系统 shall 按 §四选定路径返回与 PG+pgvector 环境相当的召回结果（召回率差异在评估阶段设定的阈值内） |
| AC-5 | When 从 PG 迁移存量数据到信创库，the 迁移 shall 通过行数与抽样一致性校验，无数据丢失/截断 |
| AC-6 | The 同一份业务代码 shall 通过 profile 切换支持 PG 与信创库，无需维护两套代码分支 |

## 七、决策边界与红线

- **数据库选型（DEC-006）属采购/监管决策**，AI 仅提供技术兼容性评估与工作量估算，**不做选型决策**（AGENTS §5 红线 7）。
- **schema 变更 / 数据迁移属红线操作**（AGENTS §5 红线 3），任何实际迁移执行须经明确授权，本文仅为设计预案。
- **迁移不得降低多租户隔离与数据安全强度**，达梦 schema 语义差异导致的隔离方案调整须单独安全评审。
