## 1. 部署架构总览

### 1.1 演进路线

| 阶段 | 编排方案 | 适用场景 | 状态 |
|------|---------|---------|------|
| 开发/自测 | `docker-compose.yml`（一键全栈） | 本地开发、功能验证 | 🟩 已落地 |
| 试点 | `docker-compose.test.yml`（轻量，不含 voice/tts） | 公网演示、内部试用 | 🟩 已落地 |
| 商用 | `docker-compose.prod.yml`（完整，含 voice/tts + HTTPS） | 生产运营 | 🟩 已落地 |
| 规模化 | Kubernetes（弹性伸缩、高可用） | 多学校规模化 | ⬜ 设计预留 |

> 单体 Compose 试点与模块化单体架构匹配，降低运维门槛；K8s 仅为规模化阶段方向，**不提前引入**（YAGNI）。

### 1.2 私有化部署模式（多校交付形态）

| 模式 | 规模 | 部署方式 |
|------|------|---------|
| All-in-One | ≤500 人/校 | 单机 Docker Compose（默认模式） |
| 分离部署 | 500-2000 人/校 | 应用/数据库/语音边车分机部署 |
| 容器化 | 集团多校 | 每校独立租户 + 独立实例，或共享实例行级隔离（07 文档 A 路线） |

### 1.3 部署形态矩阵

| 形态 | compose 文件 | 包含服务 | 访问方式 |
|------|-------------|---------|---------|
| 本地开发 | `deploy/docker-compose.yml` | postgres + redis + tts + voice + backend + frontend + nginx | `http://localhost`（学生端）/`/teacher`（教师端） |
| 测试环境 | `deploy/docker-compose.test.yml` | postgres + redis + backend + frontend + nginx（**不含 voice/tts**） | `http://<公网IP>`，HTTP |

| 监控栈 | `deploy/docker-compose.monitoring.yml` | prometheus + grafana + alertmanager | Grafana `:3002`（admin/密码） |

## 5. CI/CD 流水线

### 5.1 流程

```
开发者 git push main（或 PR → merge main）
        │
        ▼
┌──────────────────────────────────┐
│ GitHub Actions CI（ci.yml）        │  ← 质量门禁：后端编译/测试/覆盖率、
│ 全绿后人工触发本地部署              │     前端三端构建/测试、Python pytest、
└──────────────────────────────────┘     Trivy 依赖扫描（文档类变更跳过）
        │（人工执行）
        ▼
┌──────────────────────────────────┐
│ 本地 ./deploy.sh（唯一发布通道）    │
│ 1. git diff 变更检测（组件映射）    │
│ 2. rsync 增量同步源码              │
│ 3. 服务器 compose 本地构建（重试3次）│
│ 4. service-manager 重启 + 健康检查  │
│ 5. nginx reload + 路径校验         │
└──────────────────────────────────┘
        ▼
│   阿里云 ECS：postgres/redis/backend/nginx（+voice/tts）│
```

> ⚠️ 2026-08-07 决策反转（DOC-063，doing/72 取消CD）：CD 自动发布取消，deploy.sh 为唯一发布通道——服务器 3Mbps 出口限速下 CD 镜像 pull 模型成本远大于收益（voice 2.26GB 全量拉取 36min+ 且 GHCR 抖动整次失败），详见 §5.3。

### 5.2 CI（ci.yml）

- 触发：push main/develop + PR（main/develop）；**文档类变更跳过**（design/doc/docs/reports/tmp/data/根级 *.md paths-ignore，2026-08-07 G2）
- 内容：后端编译 + 全量测试（surefire/failsafe）+ JaCoCo 覆盖率门禁（整体 ≥45%、核心 service 层 ≥60%）；前端四应用构建 + lint + test:coverage 门禁；Python tts/voice pytest；Trivy 漏洞扫描（CRITICAL/HIGH 阻断）；**docker-build-smoke**（构建 tts/voice 镜像，只 build 不推送，复用 pip cache——DA-01+DA-07 结构性拦截，2026-08-08；config_loader/metrics_common 双份 diff 门禁已随 py-common 单源化移除，S-019 doing/93，2026-08-13 台账修正）；**shell-tools-test**（`bash tests/unit/scripts/*-test.sh tests/unit/backup-common.sh`，glob 全跑 15 件套 + backup-common，自带 temp repo/mock docker，<2min——DA-05，2026-08-08；verify-config-passthrough 为 D-10 接线；verify-model-names 为 DA-09 模型名单一事实源断言（config.yaml 权威 → 消费点）；deploy-lib 为 DA-11 发布链纯函数测试；verify-remote-dir/verify-nginx-host/verify-ser-enabled 为 DA-12/13/15 接线，全部 2026-08-08）
- 缓存（2026-08-07 优化 G1/G3/G4，doing/72 取消CD §9）：Maven 单缓存（setup-java cache:maven，删除手动重复缓存）；npm（setup-node cache:npm 三端独立）；pip（actions/cache，key = service + requirements 文件 hash，两服务独立）；postgres 健康探测间隔 5s
- 目的：合并前发现编译/构建/测试问题，纯质量门禁（无镜像构建推送，与部署通道解耦）

### 5.3 CD（cd.yml）——已取消（2026-08-07 决策反转，doing/72 取消CD）

- **状态**：cd.yml 已删除（DOC-063），GitHub Actions 仅保留 CI
- **取消理由**：服务器→GHCR 拉取带宽 ~1MB/s（3Mbps 出口限速典型表现），voice 镜像 2.26GB 全量拉取 36 分钟以上且 GHCR 网络抖动（unexpected EOF）整次失败；CD 全量恢复实测 70min+ 服务中断 ~40min——镜像 pull 模型在低带宽单服务器场景是结构性劣势（依据与 14 坑处置归属见 his/72 取消CD §2）
- **替代**：deploy.sh 唯一发布通道——源码增量同步（MB 级）+ 服务器本地构建（layer 缓存命中），跨网传输量从 GB 级降到 MB 级；验证闭环等价（变更检测 / 构建失败即中止服务不中断 / service-manager 健康检查 / nginx reload + 路径校验 / 部署状态文件），链路短一半
- **回滚语义**：构建失败就地回滚 `./deploy.sh --rollback <backend|tts|voice>`（服务器源码重建）；版本回退 `git revert <bad_commit> && git push && ./deploy.sh`

### 5.8 部署可观测性与监控模型（doing/80，DOC-077，2026-08-08）

**背景**：deploy.sh 无步骤耗时统计、无日志留存、无历史基线，部署变坏不可见（doing/72 全量 36min 教训只能靠记忆）。

**计时与日志**：
- 12 个部署步骤计时点（precheck/detect/compile-backend/prepare-models/build-student/build-teacher/build-parent/rsync/build-images/restart/smoke/nginx-check），毫秒取时（python3，macOS date 无 %N）；步骤按实际部署组件动态出现，未执行不计时不判
- 全量输出 tee 到 `logs/deploy/deploy-<ts>.log`（gitignore 不入库）；日志末尾追加结构化统计段（`deploy_result=`/`deploy_components=`/`deploy_duration_ms=`/`step_<key>_ms=`/`signal=`/`signal_details=`）供基线解析；部署成功时 `.deploy-state` 追加统计快照（LAST_DEPLOY_DURATION_MS/LAST_DEPLOY_SIGNAL/LAST_STEP_<KEY>_MS）
- 编排出口 `dm_finish_deploy`（库内函数，deploy.sh `trap EXIT` 调用）：失败时最后未完成步骤自动推导为失败步骤，成功/失败均输出汇报与统计段；门禁拦截（未 commit/未 push 等）保持快速失败不汇报

**监控模型（变坏判定）**：
- 基线：日志最近 10 次 `step_*_ms=`；统计 mean/p90（样本<3 用 max 替代）/max
- 阈值：无基线 → 超绝对阈值 WARN、超 2× CRITICAL；有基线 → 超 max(p90×1.5, 绝对) WARN、超 max(p90×2, 绝对×2) CRITICAL；绝对阈值表见 his/80 §2.1（调整需同步设计）
- 信号分级：存在 CRITICAL 步骤 → CRITICAL；存在 WARN → WARN；否则 OK；部署失败强制 CRITICAL

**固定格式汇报**（部署结束统一输出，含步骤明细条形图）：组件/结果（含失败步骤）/总耗时/步骤明细/信号/建议/日志路径；失败时按失败模式知识库输出修复指引（特征匹配：`code=20003` 同意闭环 / `TS2741` / `NoResourceFoundException` / `tts/personas` 403 / WeCom webhook / `HttpMessageNotReadableException`）

**自动修复完善（幂等安全边界内，红线不破）**：
- L2 rsync 降速自愈：常规 2 次失败自动 `--bwlimit=4096` 重试（3Mbps 上行教训 doing/72）
- L3 镜像构建清缓存自愈：3 次失败后 `docker builder prune -f` 再重试 2 次（幂等，无业务风险）
- L4 失败模式知识库自动输出修复指引；不做自动回滚/自动审批（发布审批人工红线）

### 5.9 部署日志审计与回归分析（his/81，DOC-078，2026-08-08）

**背景**：§5.8 监控模型给出单次部署的信号，但日志是哑数据——没有跨部署的回归分析：失败模式靠人肉翻日志、变坏趋势无检测、日志无上限。

**审计模型**（每次部署结束 `trap EXIT` 链第二步自动执行，与退出码无关，失败部署同样审计）：
- 窗口：`logs/deploy/deploy-*.log` 最近 10 次（文件名 YYYYMMDD-HHMMSS 字典序即时间序）；`dm_audit_parse` 输出记录行（basename|result|signal|steps|has_stats|has_report）
- 编排：`dm_audit_run` → 解析窗口 → A1 日志轮转（上限 50 份）→ `dm_audit_report` 生成审计报告 + 终端摘要

**回归规则表 R1-R6**（唯一事实源 his/81 §2.2，调整需同步设计）：
- R1 步骤耗时回归：本次各步骤 vs 历史基线（复用 `dm_judge`，基线排除本次日志防自污染）→ WARN/CRITICAL
- R2 部署成功率：窗口成功率 <80% WARN、<60% CRITICAL
- R3 失败模式聚类：`DM_DIAG_FEATURES` 特征计数 ≥3 次 → WARN（与 dm_diagnose 同源，单一事实源）
- R4 耗时趋势：最近 5 次同步骤连续 3 次上升 → WARN（变坏预警）
- R5 信号漂移：窗口非 OK 信号 ≥50% → WARN
- R6 日志完整性：有部署汇报但缺统计段 >2 份 → WARN（出口链路异常）

**固定格式审计报告**：全文落盘 `logs/deploy/audit-<ts>.md`（gitignore 不入库），终端摘要 5 行（结论/样本/修复/报告）；报告含审计时间/日志窗口/部署样本/回归项 6 行/结论/问题清单/修复动作/审计依据，问题按 [Pn][LEVEL] 编号并附建议。

**主动修复分级**：
- A1 自动执行：日志轮转（deploy-*.log 超 50 份删最旧，仅运行时产物 gitignored 安全）
- A2 自动输出指引：问题清单按步骤原因映射 + 失败模式知识库输出修复建议（build-images→磁盘/网络、rsync→上行带宽、smoke→LLM/TTS、restart→voice 模型）
- 不做 A0 自动回滚：生产变更人工红线（§5 红线不变）

## 11. 环境变量治理（配置纳管纪律）

### 11.1 三层归属

| 层 | 载体 | 职责 |
|----|------|------|
| 密钥层 | `deploy/.env`（不入 Git） | 密钥/凭证，12-Factor 铁律 |
| 服务层 | `application.yml` / `config.yaml` | 业务参数、阈值、音色矩阵 |
| 运行时层 | `GET /api/v1/system/config` | 前端运行时下发（5min 缓存） |

### 11.2 铁律

1. **docker-compose 是 env 到容器的唯一桥梁**：`.env` 中定义但 compose 未透传的变量 = 死变量（历史缺陷 E1：WECOM 四变量未透传导致容器企微 OAuth 永远 501，已修复）。
2. **启动决策不可延迟**：控制是否加载数 GB 模型的开关（`ASR_ENGINE`/`SER_ENABLED`）必须为 env，不能等 config.yaml 读取后再决定。
3. **env 可覆盖一切，但不应重复定义**：`application.yml`/`config.yaml` 已有默认值的参数，`.env` 仅标注「可选覆盖」（`LLM_PRIMARY_BASE_URL`/`LLM_PRIMARY_MODEL`/`DASHSCOPE_TTS_MODEL`，旧名 LLM_BASE_URL/LLM_MODEL deprecated）。
4. **密钥不落文件**：API Key/密码/Token 只经环境变量注入，配置文件只写 `${ENV_VAR}` 占位引用。
5. **变量名必须与占位符完全一致**：`LLM_PRIMARY_API_KEY` 写成 `SPRING_AI_DEEPSEEK_*`、`TTS_SERVICE_URL` 写成 `MINDSAFE_TTS_SERVICE_URL` 时 Spring 松散绑定匹配不上，将静默回落默认值。

### 11.3 环境变量归属决策矩阵（摘要）

| 变量 | 决策 | 理由 |
|------|------|------|
| DB/REDIS 密码、JWT_SECRET、ENCRYPTION_*、各 API Key | ✅ 必须 env | 密钥凭证 |
| SMS_PROVIDER / MINDSAFE_CONSENT_TRIAL_AUTO_GRANT | ✅ 保留 env | 跨环境不同（dev=logging / prod 默认 logging；启用 aliyun 时在 .env 设 SMS_PROVIDER=aliyun + 4 个 MINDSAFE_SMS_ALIYUN_* 凭证；2026-08-06 设计修正：原 prod compose 默认 aliyun fail-closed 改为 logging，因试点期 SMS 未启用、无 aliyun 凭证会卡住部署） |
| ASR_ENGINE / SER_ENABLED | ✅ 保留 env | 控制启动时模型加载（内存决策） |
| VOICE/TTS_SERVICE_URL、HTTP/HTTPS_PORT、MODEL_CACHE_DIR、VOICE_MEMORY_LIMIT | ✅ 保留 env | 容器网络拓扑与 compose 直接使用 |
| CORS_ORIGINS | ✅ 保留 env | 环境差异大 |
| LLM_PRIMARY_BASE_URL / LLM_PRIMARY_MODEL / DASHSCOPE_TTS_MODEL | 🟡 可选 env | 配置已有同默认值，仅切换时覆盖（旧名 LLM_BASE_URL / LLM_MODEL deprecated） |
| WECOM_CORP_ID / AGENT_ID / REDIRECT_URI / ALERT_WECOM_WEBHOOK_URL | 🟡 可选 env | 半公开标识符，统一填写 |

### 13.2 模型宿主机缓存（不打入镜像）

```yaml
# deploy/docker-compose.prod.yml
voice-service:
  volumes:
    - ${MODEL_CACHE_DIR:-./cache/modelscope}:/home/appuser/.cache/modelscope
```

```bash

```

> 镜像体积从 ~5GB 降至 ~2GB（P3-31）；模型持久化在宿主机，重建容器不需重新下载。

### 13.3 BuildKit pip/apt 加速

Python 服务 Dockerfile 同时启用 BuildKit cache mount 缓存 **pip 与 apt**，源头走国内镜像：

```dockerfile
# syntax=docker/dockerfile:1

# 系统包：apt cache mount + 阿里云 APT 镜像（避免 ffmpeg/torch 等重包重新下载）
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    sed -i 's|http://deb.debian.org|https://mirrors.aliyun.com|g' /etc/apt/sources.list.d/debian.sources \
    && apt-get update \
    && apt-get install -y --no-install-recommends \
        libsndfile1 ffmpeg

# Python 包：pip cache mount + 阿里云 PyPI 镜像（requirements-lite.txt：2026-08-13 台账修正，原 requirements.txt 表述与 Dockerfile/CI 实态不符）
RUN --mount=type=cache,target=/root/.cache/pip \
    pip config set global.index-url https://mirrors.aliyun.com/pypi/simple/ \
    && pip install -r requirements-lite.txt
```

- **APT 阿里云镜像**：`mirrors.aliyun.com/debian`（与镜像版本同源，跟随 Python 镜像的 Debian trixie/bookworm）
- **PyPI 阿里云镜像**：`mirrors.aliyun.com/pypi/simple/`（torch 专用 `-f mirrors.aliyun.com/pytorch-wheels/cpu/`）
