当前仓库处于“根编排层 + 设计文档”阶段，后端 `backend/` 与前端 `apps/` 目录均为空占位，**尚未存在任何运行时配置加载代码**。本仓库对配置系统的约定全部以设计文档和结构契约的形式固化在顶层文件中，属于“规划态”配置体系。

已发现的配置相关约定如下：
- **环境变量与密钥管理**：STRUCTURE.md §4.4 明确 `.env` 等密钥文件禁止入库（`.gitignore` 第 9–11 行已拦截），示例配置使用 `.env.example`；LLM API Key 一律走环境变量，禁止硬编码。
- **后端技术栈与配置位置**：STRUCTURE.md §2.5 规定后端为 Java 21 + Spring Boot 3 + Maven 多模块，`counseling-app` 启动模块负责“配置、打包”，Spring AI 采用“配置驱动、供应商无关”接入方式（决策 #7），主备降级策略见 design/13 §6.2。
- **多租户隔离**：按 design/07 采用 Schema 级隔离（`tenant_{tenant_id}`），动态数据源路由位于 `counseling-tenant/`，意味着运行时需根据租户上下文切换数据库连接配置。
- **前端构建配置**：design/17 列出 `tailwind.config.ts`、`vite.config.ts`、`tsconfig.json` 等前端配置文件，但 `apps/` 尚未创建。
- **运行时可配置项（API 暴露）**：design/16 定义了 `/api/v1/admin/config/risk-rules`、`/api/v1/admin/config/notification-channels` 等管理员配置接口，表明风险规则与通知渠道将在运行时通过 REST 配置。
- **Prompt 策略文件**：design/02 中提及 `policy/policy_zh-CN_v1.0.0.yaml` 作为 Prompt 策略的 YAML 载体，属于“业务配置即代码”的一种形式。

由于 `backend/` 与 `apps/` 均为空目录，目前不存在实际的 `application.yml`、`application.properties`、`pom.xml`、`package.json` 等具体配置文件，所有配置约定仍停留在文档与结构契约层面。
