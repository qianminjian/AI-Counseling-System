# ai-behavior.md - AI 编码行为准则

> 加载方式：模型决策（Model Decision）
> 触发场景：编码 / 调试 / 重构 / 测试编写 / 任何涉及修改源码的任务
> 来源：整合自 Claude Code `rules/ai-behavior.md`

---

## 1. 编码前思考（Think Before Coding）

**不要假设。不要隐藏困惑。公开权衡。**

- 明确陈述假设。不确定就提问
- 存在多种解释时，呈现它们——不静默选择
- 存在更简单的方法时指出。有理由时提出反对
- 不清楚时停下来，说出困惑的点并提问
- 评估方案时主动指出对 KISS/YAGNI/SOLID/DRY 的应用或潜在违背

**验证**：编码前是否有「假设 / 多解 / 不确定」显式记录。

---

## 2. 简单优先（Simplicity First）

**最小化代码解决问题。不做推测性实现。**

- 不添加超出需求的特性
- 不为单次使用的代码创建抽象
- 不添加未被请求的"灵活性"或"可配置性"
- 不处理不可能发生的错误场景
- 能写 50 行却写了 200 行 → 重写

**验证**：自问「资深工程师会说这太复杂了吗？」

---

## 3. 精准修改（Surgical Changes）

**只触碰必须修改的部分。匹配现有风格。**

- 不要"改进"相邻代码、注释或格式
- 不要重构没有问题的部分
- 匹配现有风格，即使你会用不同方式实现
- 发现无关的死代码 → 提及，不要删除

**验证**：每一行修改都能追溯到用户需求。

---

## 4. 目标驱动执行（Goal-Driven Execution）

**把模糊任务翻译成可验证目标。**

| 模糊指令 | 翻译为 |
|---------|-------|
| "加验证" | "为无效输入写测试 → 让测试通过" |
| "修 bug" | "写复现 bug 的测试 → 让测试通过" |
| "重构 X" | "重构前后测试都通过" |

多步骤任务简述计划：

```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

---

## 5. 冲突优先级

从高到低：

1. **编码前思考**（§1）— 假设与多解优先
2. **简单优先**（§2）— 不做多余实现
3. **精准修改**（§3）— 不动无关代码
4. **目标驱动**（§4）— 翻译为可验证目标

冲突示例：

- 相邻代码很丑（违反 §2）→ **§3 > §2**，不擅自改
- 最少量代码（§2）vs 完整测试覆盖（§4）→ **§4 > §2**

---

## 6. 通用例外

| 场景 | 豁免理由 |
|------|---------|
| 第三方库回调 | 接口由库定义，无法简化 |
| 性能关键热路径 | 需要 benchmark 验证 |
| IDE 生成的 boilerplate | 自动生成代码，勿手改 |
| 红线场景 | 红线优先于一切 |

需在回复中说明豁免原因。

---

## 7. 编码前 5 检查

1. 读相关文件，理解现有结构 → 参见 §1
2. 明确要改的最小范围 → 参见 §3
3. 列出关键假设，让用户确认 → 参见 §1
4. 列出验收标准 → 参见 §4
5. 检查不破坏现有测试

---

## 8. 编码后 5 检查

1. 跑测试确认通过
2. 跑 lint 确认无新错误
3. 检查无调试语句残留（`console.log` / `print`）
4. 检查无密钥 / 硬编码
5. 自问「这一行修改能追溯到用户需求吗？」

完整验证流程见 `code-engineering.md` §8-9。

---

## 9. 工具使用纪律

### 9.1 编辑工具优先级

- **Edit**：修改已有文件（必须先 Read）
- **Write**：仅用于新建文件或完整重写

### 9.2 并行与串行

- 并行调用相互独立的工具（默认）
- 有依赖任务必须串行（先 Read → 后 Edit）
- 并行上限 3（避免混乱）

### 9.3 验证后再说完成

- 编辑文件 ≠ 任务完成
- 必须跑测试/lint/启动验证才能说"完成"
- 不能验证的（如 UI）必须明确告知用户

## 10. 思维方法论

| 原则 | 简述 |
|------|------|
| 系统性分析 | 先梳理整体架构、模块边界、依赖，再深入关键细节 |
| 前瞻性思维 | 评估技术选型对性能/扩展性/成本/迭代节奏的长期影响 |
| 风险评估 | 识别可靠性/安全性/性能/发布风险，提出预防与监测措施 |
| 多角度考量 | 从技术/业务/UX/运维/治理多维综合判断 |
| 授人以渔 | 在结论外描述思路/原理/通用方法/学习路径 |
| 提问引导 | 信息不足时先提问澄清，带用户一起确认关键假设 |

---

## 11. 前置安全闸门

每次 Edit / Write 前快速自检：

1. **敏感信息**：待写入内容是否含密钥/token/身份证号/手机号/银行卡号？→ 命中则停止
2. **硬编码凭据**：密码/连接串是否直接写在代码里？→ 必须从环境变量读取
3. **注入风险**：是否拼接 SQL/shell 命令/HTML 字符串？→ 参数化查询/编码替代

详细检测规则见 `core-red-lines.md` §3。
