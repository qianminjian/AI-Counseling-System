# design-document-management.md - 子设计文档工作流协议

> 加载方式：模型决策（Model Decision）
> 触发场景：讨论新主题需单独设计文档 / 按子文档开发并迭代设计 / 开发完成主动发起"合并设计文档"
> 关联规则：`design-persistence.md`（设计持久化与 BEACON）、`core-red-lines.md` §4.5（设计文档与代码一致底线）

---

## 1. 核心原则

12 份主设计文档（`design/01-12*.md`）是**合并后的单一事实源**；进行中的主题设计一律下沉到 `design/doing/` 子文档，开发完成经「合并设计文档」后才允许回流主文档。

## 2. 子设计文档生成（第 1 条）

- 讨论某个主题需单独设计文档时，**允许独立生成**，存档于 `design/doing/`
- 编号规则沿用原分散设计文档的连续编号：`design/doing/<序号>_<主题>.md`（如 `58_xxx.md`，接续 01-57）
- 生成的子文档不并入 12 份主文档，主文档保持冻结

## 3. 开发期迭代约束（第 2 条）

- 按子设计文档进行开发；过程中反复迭代修改设计文档时，**只修改该子文档**，或在 `design/doing/` 下**新增**新的子设计文档（如 `59_xxx.md`、`60_xxx.md`）
- **不允许修改 12 份主设计文档**（`design/01-12*.md`），无论迭代多少轮
- 例外：文档管理本身的结构性变更（目录、导航、编号对照、归档位置）走导航文件（`DESIGN-OVERVIEW.md` / `STRUCTURE.md` / `TASK-TRACKER.md`），不属于主文档内容修改

## 4. 合并流程（第 3 条）

- 触发：开发完成时，由**开发人员主动发起**「合并设计文档」；AI 不得自行发起合并
- 执行步骤：
  1. 将 `design/doing/` 下子设计文档按内容归属，合并进 12 份主文档对应主题
  2. **只合并最终态的结果方案**，不合并过程数据（中间版本、备选方案、演进记录、讨论痕迹不进入主文档）
  3. 合并完成并核对后，`design/doing/` 下子设计文档归档至 `design/his/`
- 合并时同步：`DESIGN-OVERVIEW.md` 编号对照与目录、`TASK-TRACKER.md` 登记 DOC 编号、`BEACON.md` 状态

## 5. 目录约定

```
design/
  doing/        ← 进行中的子设计文档（编号接续 01-57，独立生成与迭代）
  his/          ← 归档区（历史文档 + 已合并子文档，只读溯源）
  01-12*.md     ← 主设计文档（合并后单一事实源，开发期冻结）
  frozen/       ← 冻结区（远期任务，触发条件未到不实施不合并）
```

## 6. 合并后验证清单

- [ ] `design/doing/` 已清空（仅剩 `.gitkeep`）
- [ ] 主文档仅含最终态结果方案，无过程数据
- [ ] 子设计文档已归档 `design/his/`，编号可追溯
- [ ] `TASK-TRACKER.md` 已登记 DOC 编号
- [ ] `DESIGN-OVERVIEW.md` 编号对照与目录已同步
