# think-deep.md - 深度思考分层

> 引用方式：`@think-deep`
> 触发场景：使用 `/tp` `/tt` `/ttt` `/tttt` 命令 / 复杂任务规划 / 用户要求深度思考
> 来源：整合自 Claude Code `rules/context-management.md` §6 + `rules/work-management.md` §5 模式系统

---

## 1. 四档深度思考

| 命令 | thinking budget | 适用场景 |
|------|----------------|---------|
| `/tp` | ~2K tokens | 新增功能，标准设计 |
| `/tt` | ~4K tokens | Bug 修复，硬思考 |
| `/ttt` | ~8K tokens | 复杂工作，深度审计 |
| `/tttt` | ~16K tokens | 大型重构，极致思考 |

---

## 2. 任务复杂度评估

### 2.1 评估维度

| 维度 | 简单 | 中等 | 复杂 |
|------|------|------|------|
| **改动范围** | 单文件单函数 | 多文件但同模块 | 跨模块 / 跨服务 |
| **影响用户** | 0-1 个 | 部分用户 | 全量用户 |
| **可逆性** | 完全可逆 | 部分可逆 | 难以回滚 |
| **依赖** | 无外部依赖 | 1-2 个内部依赖 | 多个外部系统 |
| **不确定性** | 需求清晰 | 部分模糊 | 高度模糊 |
| **业务影响** | 无业务影响 | 局部影响 | 核心业务 |

### 2.2 复杂度 → 思考档位映射

| 复杂度 | 推荐档位 | 思考深度要求 |
|--------|---------|------------|
| 简单（1-2 个简单维度） | `/tp` | 列出方案 + 直接做 |
| 中等（3-4 个中等维度） | `/tt` / `/ttt` | 多方案对比 + 风险分析 + 替代方案 |
| 复杂（≥5 个维度含"高度模糊"） | `/ttt` / `/tttt` | 全面分析 + 多解对比 + 风险矩阵 + 决策树 |

## 3. 各档位执行协议

### 3.1 `/tp`（思考一次）—— 2K tokens

适用：标准功能实现、明确需求

```
思考内容：
1. 需求理解（1-2 句）
2. 实现方案（1 个）
3. 关键风险（1-3 条）
4. 验证方式（1 句）

输出格式：
- 方案：[X]
- 风险：[Y]
- 验证：[Z]
```

### 3.2 `/tt`（思考两次）—— 4K tokens

适用：Bug 修复、边界条件多

```
思考内容：
1. 问题根因分析（5 Why）
2. 修复方案对比（≥2 个）
3. 回归测试设计
4. 副作用评估

输出格式：
- 根因：[X]
- 方案对比：[A vs B，推荐 A]
- 回归测试：[具体用例]
- 副作用：[Y / 无]
```

### 3.3 `/ttt`（思考三次）—— 8K tokens

适用：复杂功能、深度审计

```
思考内容：
1. 多维度分析（性能/安全/可维护性/扩展性）
2. 架构方案对比（≥3 个）
3. 风险矩阵
4. 实施路径（含 rollback 节点）
5. 长期影响评估

输出格式：
- 维度分析：[矩阵]
- 方案对比：[A vs B vs C]
- 风险矩阵：[表格]
- 实施路径：[节点列表]
- 长期影响：[评估]
```

### 3.4 `/tttt`（思考四次）—— 16K tokens

适用：大型重构、跨系统改造

```
思考内容：
1. 全局影响面分析
2. 架构级方案对比（≥3 个，含激进 vs 保守）
3. 分阶段实施计划
4. 风险与缓解（含 AB 测试、回滚预案）
5. 团队协作影响（沟通成本、文档、培训）
6. 长期演进路径（未来 1-3 年的扩展性）

输出格式：
- 影响面：[分层分析]
- 架构方案：[矩阵 + 推荐]
- 实施计划：[阶段 + 节点]
- 风险缓解：[矩阵]
- 团队影响：[评估]
- 演进路径：[1-3 年 roadmap]
```

## 4. 思考与执行的关系

### 4.1 Interact 模式（默认）

- 思考深度由用户消息中的指令决定
- `/tp` → 短思考后执行
- 用户没说 → 默认 `/tp` 级别

### 4.2 Review 模式

- 思考 + 输出审查报告
- 不直接执行修改
- 复杂度评估 = `/ttt` 起步

### 4.3 Pipeline 模式

- 思考被压缩
- 每阶段只做最小思考
- 红线场景下才升级到 `/tt` / `/ttt`

---

## 5. 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 小任务用 `/tttt` | 浪费 token，输出冗长 | 用 `/tp` |
| 大任务用 `/tp` | 思考不足，方案有缺陷 | 用 `/ttt` / `/tttt` |
| 跳过思考直接执行 | 漏掉边界条件 | 任何修改前至少 `/tp` 思考 |
| 过度思考不执行 | 拖延交付 | 思考后立即执行，不要"再想想" |

## 6. 选择指南（决策树）

```
任务复杂度？
├─ 简单（单文件/明确需求）→ /tp
├─ 中等（多文件/bug 修复）→ /tt
├─ 复杂（跨模块/新功能）→ /ttt
└─ 极复杂（架构/重构）→ /tttt

用户给的指令？
├─ "想想" / "分析下" → /tp 或 /tt
├─ "深度分析" / "全面评估" → /ttt
└─ "极致思考" / "重构架构" → /tttt

场景特征？
├─ 模糊需求 → /ttt（多解分析）
├─ Bug 修复 → /tt（5 Why）
├─ 性能优化 → /ttt（多维度）
└─ 紧急修复 → /tp（快速决策）
```
