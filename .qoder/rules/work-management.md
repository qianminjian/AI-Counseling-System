## §1 任务启动：三问锚定目标

**规则**：用户给出任务指令时，**第一步问"产出/目的"，第二步排计划**。不接受"全面测试/分析/优化"这类模糊词直接开干。

### 三问

1. **"产出是什么？"**——用户拿到产出后能做什么具体决策/动作？
   - 模糊词"测试/分析/优化/整理"必须先翻译成具体产出（"测试→规则集 / 质量报告 / 编译验证"），再让用户确认
2. **"目标的对齐物是什么？"**——成功标准是用户的目标还是任务的过程指标？
   - 错误：以"完成 T1/T2/T3"为成功标准 → 任务完成但目标未达成
   - 正确：以"用户的某个具体问题被解决"为成功标准
3. **"范围边界在哪？"**——什么**不做**也要明确说出来
   - 默认假设"全面=全模块"会导致范围爆炸
   - 必须主动声明"本次不做 X / 不深入 Y"，让用户有机会纠正

### 正反例

| 场景 | 反例 | 正例 |
|------|------|------|
| 模糊指令 | "测试一下" → 直接列 6 个任务 | "你说'测试'，我理解是为 [目的 A]，产出 [X]。如果是 [目的 B] 产出 [Y]，请确认" |
| 范围声明 | 默认"全面=全模块"导致范围爆炸 | "本次做 [P/Q/R]，**不做** [S/T]，可以吗？" |
| 卡住时 | 只想"怎么修通"不想"是否还需要修通" | 每个子任务都对照目标审视 |

## §2 执行中：范围控制与失败升级

### 2.1 任务列表 ≥4 项 → 目标对齐检查

**规则**：分解为 ≥4 个子任务后，每个子任务用 1 行说明"它直接产出用户能用的什么"——写不出来就砍掉。如果某子任务只是为另一个子任务做铺垫、而后者也服务不了目标 → 整链砍。

### 2.2 用户中途纠正 → 强制回溯

**规则**：用户纠正方向时，**必须立即回头审所有相关的已计划/已完成子任务**，不能只改当前任务。

- 自问："这是孤立问题还是系统问题？"
- 逐一检查已完成的同类任务，问"是否犯了同样的错误？"
- 发现同类问题 → 立即承认并提供修正方案，不要被动等下次纠正

### 2.3 失败升级三档

| 失败次数 | 动作 |
|---------|------|
| **第 1 次** | 正常重试 + 同时问"这个任务还需要做吗" |
| **第 2 次** | **必须**问"目标本身是否需要调整"（不是再尝试） |
| **第 3 次** | **主动停下来跟用户讨论切换路径**——禁止继续尝试不同方案 |

每次失败先列出当前假设（"我在为 X 做 Y 因为 Z"），再做下一步决策。停止判断标准：能列出 3 个失败原因都指向"目标错了"时，立刻停止。

### 2.4 执行语法闸门（长会话防惯性执行）

每次准备调用 Agent / Bash / Edit / Write 之前，**强制自问**：

> "用户最后一条消息是问句还是祈使句？"

| 类型 | 标信号 | 期望行为 |
|------|--------|---------|
| **问句** | 句末 `?` / `吗` / `？` / `行不行` / `是否可以` | **只回答，不执行** |
| **祈使句** | 句末 `。` / `！` / 无问号 + 动词开头 | 立即执行 |
| **带明确连续信号** | `继续做` / `推进` / `下一步` / `/tp` / `/atdo` | 立即执行 |
| **条件问句** | `如果 X，可以吗` / `你建议哪个` | 列出方案 + 等选 |

**反模式**：

- 问句当指令：用户问"全量测试吗" → 启动 agent（❌）
- 惯性执行：长会话后期不再等用户拍板（❌）
- 顺手做：上一指令完成不等确认就启动下一指令（❌）
- 自作主张：用户给 N 个选项 → 选一个执行（❌）

## §3 设计持久化：BEACON.md

### 3.1 项目明灯文件

每个项目的设计北方之星：`design/BEACON.md`。单一摘要文件，贯穿项目全生命周期。

```
design/
  BEACON.md          ← 唯一强制文件
  discussion/        ← 可选：多轮设计讨论摘要
  decisions/         ← 可选：详细 ADR（重大架构决策）
  reference/         ← 可选：外部参考材料
```

### 3.2 读取时机

| 触发条件 | 目的 |
|---------|------|
| Plan Mode 激活 | 恢复设计上下文 |
| 启动任何新任务 | 对照 Goals/Scope 确认方向 |
| 用户说"继续"/"接着做" | 恢复上次设计状态 |

读取后在回复中**显式引用**关键内容（如"根据 BEACON.md，当前阶段 X，核心目标 Y"），确认上下文理解正确。

### 3.3 更新时机

| 触发条件 | 更新章节 |
|---------|---------|
| 设计讨论产生新决策 | ## 设计决策 |
| 需求范围发生变化 | ## 范围边界 |
| 设计阶段推进 | ## 当前状态 |
| 新问题被识别但未解决 | ## 待解决问题 |

完整模板与规范见 `@design-persistence`。

## §4 模式系统（三模式）

### 4.1 三模式对照

| 维度 | Interact（默认） | Review | Pipeline |
|------|-----------------|--------|----------|
| 触发 | 默认 / 普通对话 | "审查 / review / 审计 / 只看不改" | "auto / 流水线 / 全自动" |
| 允许写 | ✅ | ❌ 只读 | ✅ |
| 提问 | ✅ 三问（主动澄清） | ✅ 三问（发现问题时） | ❌ 仅在红线场景停下 |
| 并行 | ✅ 充分利用 | ✅ | ❌ 严格串行 |
| 输出 | 灵活 | 审查报告模板 | 固定模板 |
| 适用 | 探索 / 设计 / 编码 / 调试 | 代码审查 / 安全审计 / 方案评审 | 重复性任务 / 自动化流水线 |

### 4.2 切换协议

| 切换 | 触发 | 行为 |
|------|------|------|
| → Review | "审查/review/审计/只看不改" | 禁用写工具 |
| → Default | "开始改/退出审查/回到编辑" | 恢复全工具 |
| → Pipeline | "auto/流水线/全自动" | 进入自动化 |
| 任意→Default | **命中红线** | 自动退出 |

### 4.3 Pipeline 工具约束（即使自动化也生效）

- **写白名单**：Write / Edit 仅当前项目目录
- **Bash 黑名单**：`rm -rf / mkfs / dd / shutdown`、外网 `curl/wget`（仅允许 localhost）、系统目录（`/etc/ /usr/ /var/lib/`）
- **文件黑名单**：`~/.ssh/ ~/.aws/ ~/.config/gcloud/`、`/etc/passwd /etc/shadow`

## §5 任务列表管理

### 5.1 何时建立任务列表

- 子任务 ≥3 项时建立
- 单任务执行可跳过

### 5.2 任务状态

| 状态 | 含义 |
|------|------|
| `pending` | 未开始 |
| `in_progress` | 进行中（最多 1 个） |
| `completed` | 完成 |
| `cancelled` | 取消（含理由） |

### 5.3 进度更新

- 完成一项 → 立即标记 `completed`
- 阻塞时 → 标记 `in_progress` + 描述阻塞项
- 不允许"完成"后才发现下游有问题
