## 1. ⚠️ 自主边界红线（7 条 - 必须先问）

即使在 auto-accept 模式下也**必须停下来问**：

| # | 触发场景 | 必须询问事项 |
|---|---------|------------|
| 1 | 删除文件、目录或 git 历史 | 删除范围、备份方案、是否有依赖 |
| 2 | 修改 .env、密钥、token、CI/CD 配置 | 影响范围、回滚方案、密钥轮换 |
| 3 | 数据库 schema 变更或数据迁移 | 迁移脚本、回滚脚本、备份验证 |
| 4 | git push / rebase / reset --hard / 强制推送 | 影响分支、是否需要 PR review |
| 5 | 安装新的全局依赖或修改系统配置 | 安装必要性、影响范围、是否可项目局部 |
| 6 | 公开发布（npm publish、部署生产、发文章） | 发布版本、审批流程、回滚预案 |
| 7 | 监管责任事项（合规判断、监管报告签署、生产发布审批） | **AI 只提供信息，不做决策** |

**触发协议**：

- 命中红线立即停下，不做任何"先做后问"的尝试
- 列出当前假设（"我准备做 X 因为 Y，因为命中红线 #N"）
- 给出 1-3 个可行方案，等用户明确决策
- 用户拒绝 → 接受并记录，不反复建议

## 2. ⚠️ 启动服务红线（端口冲突防护）

任何 `npm run dev` / `node server.js` / `next dev` / `python app.py` 等服务启动前**必须**：

```bash
# 步骤 1：检查端口占用
lsof -i:<端口>

# 步骤 2：如占用，强制杀掉
kill -9 <PID>

# 步骤 3：再次确认释放
lsof -i:<端口>

# 步骤 4：确认释放后才启动
<启动命令>
```

| 场景 | 处理 |
|------|------|
| 端口被占用 | kill -9 后再启动，不接受"端口冲突就先跑起来" |
| 残留僵尸进程 | `ps aux | grep <进程名>` 找到所有相关进程一并清理 |
| 权限不足 | `sudo` 需先获得授权（命中红线 #5） |
| **例外** | CI 容器内启动可豁免 |

## 3. ⚠️ 安全编码红线

每次 Edit / Write / Bash 前快速自检：

### 3.1 敏感信息检测

| 类别 | 检测项 | 命中动作 |
|------|--------|---------|
| 密钥/token | API key / access token / private key / Bearer token | 立即停止，拒绝写入 |
| 个人隐私 | 中国手机号（11 位）/ 身份证号（18 位）/ 银行卡号（13-19 位） | 立即停止，脱敏后重写 |
| 数据库 | DSN 连接串 / root 密码 / Redis URL 含密码 | 立即停止，从环境变量读取 |
| 系统凭据 | SSH 私钥 / .env 文件内容 | 立即停止，禁止提交 |

### 3.2 注入防护

| 类别 | 禁止做法 | 正确做法 |
|------|---------|---------|
| SQL 注入 | `query("SELECT * FROM users WHERE id=" + userId)` | 参数化查询 / ORM |
| XSS | `element.innerHTML = userInput` | `textContent` / React JSX 自动转义 |
| CSRF | 裸 POST 无 token | 校验 CSRF token 或 SameSite Cookie |
| 路径穿越 | `fs.readFile(userProvidedPath)` | `path.resolve` + 前缀白名单 |
| 命令注入 | `exec("rm -rf " + userPath)` | 禁止拼接 shell 命令字符串 |

### 3.3 硬编码凭据

- 密码/连接串必须从环境变量读取
- 测试中调用第三方付费 API 必须用 mock 隔离

## 4. 通用工程纪律（4 条）

### 4.1 改完跑验证

- 不要只改不验（具体命令见项目级 AGENTS.md 或各技术栈约定）
- 测试/lint/启动三选一至少做一项

### 4.2 不绕过报错

- 找根本原因，不注释报错或加绕过标记
- 禁止 `try { ... } catch {}` 空吞噬
- 禁止删除/跳过失败测试让 CI 变绿

### 4.3 密钥不进代码

- token / 密码 / API Key 不进代码、commit、日志
- AI 生成测试数据必须用脱敏格式（身份证 `3201**********1234` / 手机 `138****1234` / 银行卡 `6222****1234`）

### 4.4 大改动先出方案

- 涉及多文件 / 跨模块 / 架构级变更 → 先出方案，确认后再动手
- Plan Mode（@design-persistence）下产出方案 → 等用户批准

### 4.5 设计文档与代码一致（项目底线规则）

`design/*.md` 是项目的**单一事实源**，必须与代码保持一致。这是不可妥协的底线：

- **改代码必同步文档**：任何涉及类名/接口/模块职责/安全机制/数据流/Prompt 的代码变更，**同一次提交**内必须同步更新对应 `design/*.md`（尤其是各文档的"Java 实现层适配"章节）。
- **改文档必核对代码**：更新设计文档的实现描述时，必须先读真实代码确认类名/行为，**禁止凭记忆或设计稿臆测**。
- **设计期 vs 已实现要区分**：目标设计（设计期类名）与已实现（真实类名）必须明确标注状态（如"目标设计"/"M1 实际实现"/"尚未实现"），不混淆。
- **交付自检**：commit/PR 前检查"本次代码改动是否已反映到 design/"，未同步视为未完成。
- 发现文档与代码不一致时，**以代码实际行为为准**修正文档（除非代码本身是 bug）。
